# v0.6：明确规划选项、分句核对与一次修正

网页的“分析计划”默认使用新规划器，流程仍是生成草稿、核对/修改、预览、执行、下载并离线复核。自定义数据不会自动发送给网页模型。原来的单次规划器保留在评测脚本中作对照。

## 模型提案与实际计划

模型先生成平坦的`actions`，一个动作只能是`query`、`compare`、`describe`或`unsupported`。编译器转换为既有的`AnalysisPlan`，因此编辑器里的JSON仍是可执行的查询参数与步骤。下载轨迹可查看编译前提案、校验错误、修正回复及最终计划。

查询必须显式给出`metric`、`ranking`、`top_k`和`include_ties`：

| ranking | 编译结果 |
| --- | --- |
| minimum | 按指标升序，top_k=1 |
| maximum | 按指标降序，top_k=1 |
| ascending | 升序，使用给定top-k；null保留全部 |
| descending | 降序，使用给定top-k；null保留全部 |

minimum/maximum只能接受top_k为null或1；并列是否保留由明确的include_ties决定。筛选条件按原值编译，实际数据口径仍由工具验证。

比较可引用实际`run:ID`，也可直接引用前面的查询动作ID，如`q1`（兼容`step:q1`）。名称空间不混淆：动作ID不含冒号，不能被误认为实验ID；未知、未来或非查询动作引用被拒绝。前置查询必须恰好返回一条记录，否则需要明确选择。

## 分句检查的范围

服务端按分号、中文句号、问号、感叹号和换行拆分原文，保留小数、ID及逗号。新模型提案必须给每个分句分配动作；同一分句可包含多个动作，但不能同时被处理和标为未支持。原文引句由代码填入，不由模型重新抄写。

界面将完整分句与步骤关联并显示“已关联步骤”“标为未处理”“未关联完整分句”或“关联与未处理冲突”。手动编辑或历史计划的覆盖清单是提示，不会自动补写步骤；部分原文片段不当作完整分句已关联。用户可以选择执行明确的部分计划，不能把它解释成整个问题已完成。

**分句关联不等于语义覆盖**：一个分句可能要求两个查询，模型只做一个也可能通过关联检查；模型仍可能选择错误的minimum/maximum、阈值或比较对象。为此保留实际参数预览和专门的反例测试，不把all_clauses_accounted_for当作正确率。

## 调用预算与错误

`POST /api/plan/draft`最多两次模型请求。首轮格式、字段、引用或分句关联校验失败时，传回本地错误并允许一次完整替换；重复同一无效输出停止。供应商超时、HTTP错误或损坏的工具调用协议不自动重试。每次回复、失败、用量和实际调用次数都保留；失败的后续尝试不会冒用上一版计划。

页面显示本次调用次数。已有预览/执行接口仍不调用模型；它们在内存中做只读计算，用于验证引用和交付结果。预览绑定问题、计划和数据，修改后失效。

## 兼容性和复现

单查询与计划receipt格式维持v1；分句提示是派生信息，不修改旧文件的哈希和结果。测试重算了v0.5六份可执行计划receipt。已知示例仍可使用：

```bash
lablens verify result.json
pytest -q
# 以下会产生模型调用费用；guided_once最多1次，guided最多2次：
python scripts/evaluate.py --cases evaluation/benchmark-v0.6.json --split holdout --limit 4 --strategy planning --repeats 2 --workers 4
```

评测的planning组合包含旧planner、新guided_once、新guided。每次运行除了manifest哈希，还保存`frozen-source/`中的完整源文件，开发阶段未提交的代码也可检查。自动执行标为unreviewed_evaluation，不冒充人工核对。
