# v0.7：有限请求规则与可核对的修正

“分析计划”在原有分句关联之后增加“请求规则核对”。它把少量完整中文句式转换为预期查询参数，再与模型提出的步骤逐项比较。一个分句同时要求两个查询时，两项受支持请求分别核对；“原文已经关联到某个步骤”不再足以代表这些查询都已列出。

这是一组明确限定的查询规则，不是通用语义理解或整个任务完成的证明。没有匹配到支持句式时，页面显示“尚未进行请求规则核对”，不会显示全部通过。

## 支持哪些句式

每个独立查询以“列出”“查询”或“找出”开头，可加“分别”。可直接接选择要求，也可使用“筛选条件的选择要求”。规则要求匹配完整内容，不会忽略不能识别的尾句、否定或额外限制。

筛选条件有以下四类，可用“且”连接不同条件；同一字段重复出现不接受：

| 筛选原文 | 对应参数与边界 |
| --- | --- |
| 正确题数至少440 | `min_correct=440`，包含440 |
| 准确率至少95% | `min_accuracy=0.95`，包含95% |
| 准确率不高于95.2% | `max_accuracy=0.952`，包含95.2% |
| 平均长度严格小于31.6词 | `max_length=31.6`，不包含31.6 |

百分数转换为0–1的小数，数值还须通过已有查询参数验证。长度沿用快照的 `whitespace_words` 口径，不等同于 tokenizer token。

支持的选择要求如下：

| 选择原文 | 核对内容 |
| --- | --- |
| 所有记录、全部记录、所有实验、全部实验 | `top_k=null`，保留筛选后的全部记录 |
| Pareto集合、完整Pareto集合、全部Pareto集合 | `pareto_only=true` 且 `top_k=null`；可带完整后缀“（准确率更高且长度更短）” |
| 准确率最高的所有并列记录 | 准确率降序、`top_k=1`、保留边界并列 |
| 准确率最低、平均长度最长/最短、正确题数最多/最少，后接“的所有并列记录” | 对应指标和极值方向、`top_k=1`、保留边界并列；“所有”可换为“全部”，“记录”可换为“实验” |
| 记录，按平均长度升序取前2条并保留边界并列 | 指定指标、升降序、前N条及边界并列；指标可为准确率、平均长度或正确题数 |

例如，“列出正确题数至少440且准确率不高于96%的所有记录”可核对两项筛选条件与不截断结果的要求。对于“所有记录”和“Pareto集合”，规则不额外要求未指定的排序方向或并列开关；界面的参数对照只显示该项实际核对的字段。

## 同句多个查询与未核对内容

沿用现有的分句方法后，规则只用中文或英文逗号紧接“以及”拆开同句查询，例如：

> 分别列出正确题数至少440的完整Pareto集合，以及正确题数至少443的所有记录

第二项可以省略“列出”。每项必须完整匹配；其中任何一项无法识别，整个分句标为未核对。“和”“及”、单独的逗号或任意自然语言连接方式，不会自动当成两个请求。

以下内容保守地留给人工确认：

- 问题任意位置含中文引号、英文单双引号、直角引号或反引号时，整题的所有分句均不核对，避免把引用内容当成待执行要求。
- 不在上述完整句式内的表达，包括比较方向、前置结果引用、数据说明、因果和统计显著性解释。
- 同一分句的两个查询具有相同筛选范围时，无法唯一关联步骤，整句不核对。
- 无法识别的附加条件、否定、选择关系或格式变体。规则不会先截取看似熟悉的片段，再宣布该句通过。

“未核对”不代表请求错误或无法执行，只表示这些规则没有给出结论。与已识别分句没有关联的其他步骤也不属于本次规则完整性检查的范围。

## 如何关联计划与展示冲突

每个识别出的请求保留原文及其字符位置。候选查询须引用完整分句或该请求的完整片段，并具有相同筛选范围；这里也核对未请求的额外筛选是否被加入。找到唯一查询后，再核对该选择要求规定的截断、排序和并列参数。

界面在“原问题分句核对”下展示请求原文、关联步骤及以下状态：

| 状态 | 含义 |
| --- | --- |
| 已核对支持条件 | 唯一对应查询的受支持条件一致 |
| 条件不一致 | 找到对应查询，但受核对参数存在差异 |
| 缺少对应查询 | 未找到原文关联与筛选范围均匹配的查询 |
| 无法唯一匹配 | 多个查询同时对应同一请求 |

被识别分句中未能对应请求的相关查询会单独提示。参数对照使用中文字段名；冲突项默认展开，同时显示差异说明。未核对的分句始终单列，不混入通过项。

手动预览发现冲突时，执行入口仍然可用。用户可选择执行明确列出的部分步骤；结果继续保留冲突提醒，不能把“这些步骤已执行”理解为“原问题已完整完成”。问题或计划编辑后，原预览会失效，须重新预览。

## 自动生成与调用预算

`POST /api/plan/draft` 默认开启请求规则校验。模型先提出草稿，经过结构、引用和预览检查后，再执行请求规则核对；发现冲突会将本地错误反馈给模型，让它提交完整替换提案。

整个生成流程最多两次模型请求，即格式、引用、分句关联和请求规则校验合计最多触发一次修正，不是每类错误各修正一次。供应商错误、超时或损坏的工具调用协议不自动重试。第二次仍无效的提案不会获得 `needs_review` 状态；轨迹保留实际回复和错误，不能把保留供手动编辑的候选计划误当成通过校验。

底层函数 `draft_guided(..., check_request_rules=False)` 继续默认关闭规则反馈，用于保留原规划策略的评测对照。网页API显式传入 `True`。评测脚本的 `guided` 与 `checked` 使用同一提示、提案结构和最多两次请求预算；`checked` 开启本地请求规则反馈。策略开关不代表真实任务一定成功，结果须另看原始轨迹及评测报告。

预览、手动执行和离线复核均不调用模型。网页真实生成发送问题及内置数据摘要和说明，不会自动发送“条件查询”中导入的自定义数据。

## 离线体验：发现被截断的完整集合

1. 打开网页“分析计划”，点击“规则核对示例（离线）”。该按钮会替换当前问题与计划，不调用模型；原有固定示例按钮仍然保留。
2. 示例问题为“分别列出正确题数至少440的完整Pareto集合，以及正确题数至少443的所有记录；说明峰值显存测量是否记录。”
3. 示例包含两个查询与一个资料说明步骤。两个查询的 `top_k` 都为 `null`，分别处理 `min_correct=440` 的Pareto集合与 `min_correct=443` 的全部记录。查看规则区：两项查询条件可核对，峰值显存说明仍列为未核对。
4. 展开“高级：编辑计划 JSON”，将 `pareto` 步骤的 `top_k` 从 `null` 改为 `1`，其余参数保持不变。点击“预览当前计划”。
5. 规则区应显示“条件不一致”，原文要求为“不截断，保留全部”，实际参数为“前1条”。即使步骤关联覆盖了整个原文分句，这项截断仍会被指出。
6. 可将 `top_k` 改回 `null` 并重新预览；也可保留冲突，选择按所列步骤执行，观察结果仍提示原请求尚有冲突。

## 可复核结果与旧文件

计划receipt继续使用 `lablens-plan-receipt/v1`。请求规则报告由问题和计划派生，展示在预览与执行响应中，不加入receipt的固定字段，也不改写旧文件。

旧receipt复核仍检查内容哈希、数据快照及按计划重算的结果是否一致。复核成功不证明原始数据真实、模型理解正确或自然语言要求完整完成；请求规则匹配成功也不提供这些保证。

实现入口：[`request_checks.py`](../lablens/request_checks.py)、[`guided_planning.py`](../lablens/guided_planning.py)、[`planning.js`](../lablens/static/planning.js)。
