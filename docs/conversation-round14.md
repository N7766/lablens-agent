# 第十四轮：十万条任务历史、摘要分页与有界模型报告

2026-11-08，十二轮收尾的 **第 3/12 轮**。实现历史列表窄投影、工作区绑定游标和按需详情，完成三档真实 MySQL 数据规模对照。代码仍为草稿候选，主服务未升级。单题模型报告有进展，但不能据此宣布完整 Agent 或通用语义质量验收完成。

## 问题与设计

旧列表每 2.5 秒读取最近 100 条完整任务，SQL `SELECT *` 还取出并不用于列表的资料快照。报告越长，数据库/JVM解码与传输成本越高，旧接口也没有继续浏览更早历史的能力。

增加显式 `?view=summary&limit=25`，仅查询列表需要的字段；按 `created_at DESC,id DESC` 排序，使用时间与ID的联合边界继续读取，最多100条。沿用 `task_workspace(workspace_id,created_at)` 及 InnoDB 隐式主键，通过实际计划确认可逆序范围扫描，本轮未新增重复索引。摘要仍需回表，不称覆盖索引。

无参旧 API 保持兼容；单任务详情保留报告、资料版本、来源、错误和未知用量。前端默认25条、按需详情、加载更多，选择与工作区切换带竞态保护；未翻页时自动轮询最多保留25条，翻页后保留已载入记录并提示重新载入。游标绑定工作区用于防误用，不是鉴权；它表示位置，不是冻结数据库快照。

## 同条件对照

[运行前协议](evaluations/conversation-round14/history-protocol.md)固定三套隔离库，分别 1,000 / 10,000 / 100,000 条合成终态行、四个工作区、90%热点分布与同时间戳记录。**这些是直接生成的历史数据，不是执行了十万次 Agent。** 100k 的JSON逻辑字节约710.67MiB，表/索引分配约784/66.03MiB。`TABLE_ROWS=50007`只是统计估计，真实COUNT为100000；快照重复存储尚未优化。

旧版归档jar对应 `0f732e4`，候选生产实现 `51504e6`，HTTP工具冻结于 `ab6e92c`。同一规模使用同一数据库，固定12连接、2worker、200 HTTP线程、128–512MiB JVM；读取实验关闭dispatch。MySQL 9.5.0运行在同一台M4 Pro/24GiB机器，未重启MySQL或清空OS缓存，**不是冷缓存或生产容量实验**。

每规模按旧—新—新—旧（ABBA）运行，四次分别重启JVM；各端点5次预热、20次顺序读取，再8客户端各10次列表闭环读取。12个窗口的 **1,860次响应全部正确**，包含180次预热；列表ID、详情正文、精确总数均核对。每窗口全部原始值公开，不挑选较快结果。

## 功能、混合工作与浏览器

真实MySQL集成覆盖微秒时间、同时间戳、删除边界、分页中插入、跨工作区游标、完整详情和大JSON排除。浏览器验证25→50条、选取详情、刷新后25条并重新读取同一记录；62次访问全为GET，控制台无warning/error。[浏览器证据](evaluations/conversation-round14/browser/checks.json)属于合成历史读取，不是live Agent端到端验收。

ABBA结束后另做30次提交与160次摘要读取：8次受理并全部成功、22次明确queue_full拒绝，无重试，实际HTTP峰值12、worker峰值2。数据库任务ID与worker开始/完成逐项一致，0模型调用；最后100008行应拆成100000合成历史与8个真实离线任务。深页与跨工作区的额外17次只读HTTP检查也通过。混合工作不能与纯读ABBA延迟混合统计。

最终Python **1917通过**，Java **149通过、2条条件重启用例跳过**，UI **74通过**。日志与边界见[验收汇总](evaluations/conversation-round14/README.md)。

## 发送器诊断：机制明确，历史根因未确认

冻结独立[受控协议](evaluations/conversation-round14/sender-protocol.md)，共享事件循环和独立采样进程各18秒、144槽位，注入相同18次180ms阻塞观察。共享循环漏发 **6/144**、最大loop lag184.725ms；独立进程漏发 **0/144**、最大lag15.631ms。原100ms迟到门槛保持不变，两份账本、1800心跳tick与子进程退出全部对账。

这仅证明阻塞观察器可以干扰同循环发送，独立进程在本次注入下避免该干扰。实验没有HTTP或真实业务调用，不重写Round13的1次漏发，不证明其根因已定位，也不关闭[#53](https://github.com/N7766/lablens-agent/issues/53)。[原始汇总](evaluations/conversation-round14/sender/summary.json)。

## 模型：一份报告，保留格式失败与质量边界

运行前将transport门与精确输出评分分开，并冻结新合成题、评分标准、生产提示/校验器、tiny与生成载荷、复核构建规则及最多3次调用和费用上限。实际 tiny/生成/复核均HTTP200，总耗时41.771秒，共7251个已知token；没有重试或增加调用。tiny仍返回`OK.`，严格`OK`格式项仍失败，但有效传输允许按预声明计划继续RAG。[原始运行](evaluations/conversation-round14/model/run/summary.json)。

新的Finch题要求区分EXPLAIN估计、相互矛盾的延迟导出、缺失实际行数和未知索引因果。未参与出题/提示编写的另一AI审阅者判定：检索4/4，报告级语义通过，无错误整体拒答；同时指出重复结论、一条解释的定义来源引用不完整、`identical conditions`措辞偏宽。[逐项语义审阅](evaluations/conversation-round14/model/review.md)保留这三项问题，不能写成每行引用完美或泛化准确率。

这是 **1个AI编写合成问题、任务分离的AI预验收**，不是独立人工评测。运行直接BM25 RAG，未走Agent选工具或JVM持久化；上面的浏览器历史是另一组合成夹具，不能拼接成完整live Agent演示。旧严格0/6、0/4、四次超时以及Round13失败均不改。

## 实际难题与取舍

- SQL统计行数约为真实行数一半：保留估计与实际COUNT，不能拿`TABLE_ROWS`当生成量验收。
- 旧页加载、自动轮询与详情选择相互竞态：分别保留游标、选择代次与工作区范围，避免旧响应覆盖新选择或轮询无限追加DOM。还有一个可恢复边界：旧页失败后若head也失败，重试按钮会指向head；“加载更早记录”及原游标仍可用，未宣称所有UI失败组合都完善。
- 最初HTTP工具在采指标后才落盘，指标超时会丢失已经测完的请求：正式测量前改为先落155条账本和临时汇总，再独立记录各指标失败，增加超时/坏JSON/非200反例。正式12窗口诊断均完整。
- 多种验收不能共享一句“全部通过”：历史读取、合成发送器机制、直接RAG报告分别验收；独立模型格式失败和旧系统验收缺口继续保留。
