# LabLens 第九轮：规则判定与派生量审计

2026-10-31。本轮代码、工程验证、一次真实模型回归和历史回看已完成，**模型交付退步，候选不发布**。[PR #48](https://github.com/N7766/lablens-agent/pull/48)保持草稿，主服务未升级。

## 实现与背景

LabLens将研发文档、配置和实验记录纳入版本化工作区，由Agent选择工具检索、核验并输出带来源的报告。后端为Spring Boot + MySQL/Redis，Python/FastAPI负责RAG和模型循环。本轮解决的是已有排查中“资料已经拿到，回答仍被误拒、重复生成或无法追查”的问题。

- **区分验收与因果。** 新增`rule_evaluation`，要求计算、阈值和总判定分别引用测量与适用规则；保留因果机制的证据门槛。
- **派生量带证据链。** 同一对象的显式节电百分比可提供一跳数值凭证；消费行仍须自己选择相同操作数片段和公式规则，记录来源指纹与依赖。只覆盖有限语法，不证明通用语义或总验收正确。
- **逐条保留或替换。** 模型明确选择保留正确行，或返回完整替换；两组ID必须精确覆盖原稿。占位、已知错误行不能保留，恢复后执行全部检查。
- **失败也可追溯。** 实测发现失败review正文未保存，封存后以独立提交`9db927e`补了有界响应、finish_reason、校验原因与Java错误轨迹保存；保留原失败，未追加真实模型调用。

唯一成功报告的主结论正确，但缺少默认规则与部署覆盖关系解释，部分行没有选全所需规则引文。它的5行全部替换，没有真实保留收益。相比上一轮6报告+1必要澄清，交付明显下降，不能宣称优化已提升稳定性。

7份历史草稿的受控字节对照中，新协议增加请求约1.35–1.43KB；假设保留全部允许行可减少响应529–2,204 bytes，全替换则增加31 bytes。这只是JSON编码实验，不是实际token、费用、时延或语义收益。[完整报告](evaluations/conversation-round9/REPORT.md)。

## 实际难题与排查价值

两次“复核失败”均收到HTTP200，尚余约15秒/26秒；外层worker502不能被误称供应商502。因为失败正文未留存，无法再确定是格式、ID分区还是引文校验触发。另两次超时需区分“响应已回且用量已知”和“未收响应、用量未知”。补诊断时又发现畸形message触发异常，已加入负例与受控错误处理。[失败排查](evaluations/conversation-round9/assessment/failure-review.md)、[过程记录](evaluations/conversation-round9/execution-notes.md)。

Playwright只读检查确认成功报告、来源与工具轨迹可回看；刷新后重新选择历史任务，正文SHA完全相同。失败、超时及未知用量明确显示。QA关闭前后五张表的内容指纹不变，主服务健康；本轮无澄清案例，未补造验证。[浏览器证据](evaluations/conversation-round9/browser-check.md)。

## 简历素材与下一阶段

> 构建Spring Boot、MySQL/Redis与Python协作的可追溯RAG/Agent工作区，实现版本化资料、持久任务与会话、逐调用预算及来源审计；通过冻结多轮回归、真实基础设施集成和故障演练，定位引用缺口、规则误拒、复核协议失败与超时，保存原始失败及修复边界。

可以用本轮讲清协议设计、失败观测、状态一致性和证据驱动排障。不能写成高准确率、商业生产高并发、线上事故经验或完成GPU部署。

接下来先用小规模真实协议验收定位保留/替换失败，再使用范围更广的新题验证，停止仅围绕这十题扩大规则。MQ/outbox/inbox、开放负载、数据规模、记忆与私有GPU仍按[工程路线](backend-llm-capability-roadmap.md)独立实现和验收。本轮没有新增这些组件。
