## 业务主线与完成定义

将项目继续做成“团队研究/运维资料批量导入与可追溯诊断任务系统”：团队导入版本化配置、日志和结果；用户提交问题；系统异步排队、检索、调用模型和核验；用户查看来源、取消任务，并在刷新或重启后继续查看历史。资料变更、并发提交、批量导入、上游变慢和结果不确定都属于业务场景。

MySQL 保存权威业务状态，Redis 用于缓存和短时额度控制，MQ 传递可重投的业务事件，Python 执行检索与 Agent，私有模型服务提供可独立测量的推理能力。引入组件时必须对应一个已定义的问题、失败路径和验收，不以依赖数量作为工程能力指标。

“承受流量”分三层证明：可复现的合成业务流量、真实模型推理负载、经过授权的真实用户试用。三者各自记录环境和分母。没有实际试用，便只能写“负载测试验证”；故障注入和本地遇到的死锁/超时能展示排障能力，不能写成已有商业生产事故经验。

## 统一实验约定

每阶段可分一轮或多轮交付，按依赖推进。阶段通过至少要有：代码/配置版本、数据生成种子或资料哈希、运行命令、环境、原始逐请求记录、全部失败、指标计算方式和结论边界。先冻结验收条件，再运行；调参用已暴露回归，新题只用于当次验收。

| 实验层 | 请求经过什么 | 能说明什么 |
|---|---|---|
| 后端控制面负载 | HTTP → JVM → MySQL/Redis/MQ → 固定延迟或故障 worker | 接入、排队、持久化、背压、重复处理与故障恢复；外部模型调用为 0 |
| 本地检索业务负载 | 真实资料导入、索引与 BM25/向量检索 | 数据量下的检索耗时、内存和召回变化；嵌入生成是否实际调用需单列 |
| 模型服务负载 | 测试客户端 → 真实推理服务器 | TTFT、生成速率、排队、显存、服务错误；不是整条 Agent 的质量 |
| 真实 Agent 链路 | 提交 → 多次模型决策 → 工具 → 复核 → 报告持久化 | 实际任务交付、调用成本与结论质量；不能用一次模型请求吞吐替代 |
| 真实用户试用 | 已鉴权用户自己的授权操作 | 实际使用量、需求与失败；人数和反馈只能按实际记录填写 |

并发客户端数、HTTP 请求/s、任务/s、token/s 各自报告。区分计划到达量、实际发送量、接受量、429/503 拒绝量、超时、成功终态和有效答案。压测客户端来不及发出的请求不能从分母消失。闭环负载与按计划到达的开放负载分别命名；不把大量拒绝后的低延迟称作高吞吐成功。

## 阶段 1：性能诊断、业务 SLO 与资源预算

**输入：** 第三轮两次 `review_started` 后超时的原始轨迹、冻结源码与问题。它们现在是已暴露案例，只适合诊断和回归。

**具体交付：** 为决策、检索、核验、复核记录开始/结束、单调时钟耗时、剩余预算、请求字节/消息规模、已知 token、终态和未知用量；对取消/超时同样保存。用受控延迟复现预算消耗，再根据测量压缩重复上下文或改进预算分配。保持原始失败，不把超时草稿当最终答案。当前请求若非流式，只能报告完整调用耗时，不能倒推 TTFT。

定义三类用户路径：小型历史查询、异步任务接收、Agent 最终报告。先写下实验目标和允许的失败方式，再测基线。历史/接入可用 p95 500ms 作为**待验证的初始本地目标**；Agent 沿用现有总预算作为回归约束。没有测量前不写生产 SLA，也不靠单纯延长时限声称性能问题已解决。

**资源约束：** 本机本轮只读核实为 Apple M4 Pro、12 CPU、24 GiB 统一内存、macOS 26.6.2。先采集空闲内存、进程 RSS、数据库磁盘与连接池状态；阶段 1 不新增大型模型。后续本地隔离测试先以 JVM heap 1 GiB、MySQL buffer pool 2 GiB、Redis maxmemory 256 MiB 作为可调整的实验配置起点，Python/MQ 另测峰值；这些不是当前已配置值，也不等于进程总内存限制。每次运行设进程、磁盘、时间与模型调用数量上限。

**负面测试：** 慢决策、慢检索、复核未回包、取消发生在请求前/后、provider usage 缺失、输出过大；每项应有明确终态，无隐藏自动重试。

**验收指标：** 已执行的调用都有起止或超时证据；已知/未知用量不混淆；时间归属能区分本地准备、工具和上游等待；相同失败题修复前后保留完整结果。小样本列逐题耗时，不用两个样本的 p95 推断稳定性。新题交付、语义评分另外报告。

**简历证据：** 可写“定位 Agent 分阶段超时并增加预算与调用观测，保留故障复现和前后对比”。只有测量证明后，才填具体延迟改善与适用负载；当前不能断言根因是供应商慢或上下文过长。

## 阶段 2：RabbitMQ、事务 outbox 与消费幂等

**输入与实际切片：** 阶段 1 的任务状态、用量和调用观测。第十一轮先为已有诊断任务接入 `task.available.v1` 通知，用现成任务状态核验重复投递与未知模型结果保护；原规划的“批量资料导入/建立索引”保留为后续独立业务，不声称本轮已经实现。业务数据仍以 MySQL 为准。

**具体交付：** 第十一轮已实现任务与 outbox 的同事务写入，独立投递器使用 publisher confirms 与 mandatory return 处理路由失败。事件只携带 `event_id/task_id/workspace_id/schema_version/snapshot_ref` 等必要引用，避免把整份资料放进 MQ。记录投递尝试、确认和最后错误；未确认事件允许重复发送。消费者用 inbox 唯一键或任务状态条件更新去重，提交持久状态后才 ack。先实现应用轮询 outbox，只有扫描成本和需求证据成立才引入 CDC；Debezium 文档用于参考事件 ID/聚合键设计，并非本项目已经安装 Debezium。[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)、[Debezium outbox](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)。

MQ 通知与已有轮询必须共用一套数据库领取/owner 校验，不能形成两个独立模型调用入口。一次 MQ 重投不意味着允许重新调用未知结果的 LLM。纯索引任务可在有版本键和幂等写入的条件下有限重试；模型调用已经发出但结果未知时，记录不确定状态并保留显式对账/新任务路径。手工 ack、有限 prefetch、有限重试次数、延迟重试与死信查看构成完整链路。[RabbitMQ 可靠性说明](https://www.rabbitmq.com/docs/reliability)。

**验收目标（逐项以实际记录为准）：** 数据库回滚、提交后投递器崩溃、broker 已收消息但 confirm 丢失、无路由、消费事务提交后 ack 丢失、重复/乱序事件、坏消息、消费进程崩溃、已取消任务收到迟到事件。单节点可验持久化；只有实际运行多节点并做故障切换，才声称测过 quorum 高可用。[Quorum queues](https://www.rabbitmq.com/docs/quorum-queues)。

**验收指标：** 至少 1,000 个隔离合成事件加上述故障矩阵；数据库提交的事件均可对账到待投递、已确认、已消费或明确死信状态，无静默丢失；重复事件不重复业务写入；未知模型调用不被自动重发；统计投递延迟、积压最老年龄、重投/死信数量。以至少一次消息投递加业务幂等描述保证，不承诺第三方端到端 exactly-once。

**简历证据：** 事务边界图、故障时序、outbox/inbox 数据、原始 MQ/HTTP 记录，比“接入 RabbitMQ”本身更有解释力。

## 阶段 3：并发准入、背压、隔离与真实业务入口

**第十六轮身份切片（本地工程验收完成）：** 默认开启持久会话和资源权限；管理员显式接管历史无主工作区，不能读取或夺取已拥有的工作区。服务密钥保护Python全部旧、新API，Java任务/取消/索引与Agent工具调用均携带身份；原资料revision许可继续生效。53项真实跨服务检查通过，成员共用原有数据库队列限额；没有完成分布式token费用预算或公网验收。撤权对之后检查权限的新请求生效，已授权在途操作继续，详见[契约](workspace-auth.md)。

**第十二轮最小切片（本地工程验收完成）：** 在正常 HTTP 提交路径中，先查已提交幂等记录，再在事务外获得 Redis 决策，然后以 `READ_COMMITTED` 按 global guard → workspace → conversation 加锁。默认全局 1,000、每工作区 200 个活动任务，活动包括 `QUEUED/RUNNING/CANCEL_REQUESTED`。共享数据库的 JVM 必须使用一致配置；内部已有事务调用须显式 RC 且不预持其他锁。Redis 按新提交尝试计量，尚未落库的同 key 并发可能多计；数据库拒绝不退还次数。`admission` 状态的活动数有界采样、highwater 仅属本进程观测，不能作为连续全局峰值或模型费用额度。配置和拒绝契约见 [JVM 文档](../services/workspace/README.md#task-admission-and-overload)。本轮短档开放流量实验不替代下述长时间稳定性、多实例公平性和鉴权验收。

**输入：** 可靠异步链路及其可观测数据。面向团队使用前先补登录、成员/工作区权限、资料发送许可和服务间身份；对已有工作区迁移归属，不能仅在 URL 添加 tenant ID。

**具体交付：** 每租户和全局的排队上限、执行配额、模型调用/token 预算、超时与并发控制；将快查询、导入和昂贵推理分成有界资源池。先保留一个 Python worker，再实现可持久化的 worker owner、租约 fencing 和取消路由后测试多个进程。Redis 原子脚本只执行有限操作；Redis 不可用时，付费新任务采用明确拒绝或受限的数据库额度兜底，已持久任务继续按安全策略执行，不能无限放行昂贵调用。Lua 原子执行会阻塞 Redis 其他活动，不能在脚本中扫描大集合。[Redis Lua 官方说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)。

补充缓存命中验证、版本失效、热点击穿合并的对照实验；合并仅适用于内容和权限范围都一致的只读计算。LLM/Agent 报告不因 Redis 结果缓存而跳过最新资料或用户意图。明确公平调度策略，避免单个批量导入占满所有执行槽。

**负面测试：** 热租户与普通租户竞争、双实例相同幂等键、Redis 断连、连接池耗尽、慢消费者、流量突发、取消和租约过期竞态、跨租户访问、伪造 scope、缓存投毒；压测客户端和服务端都要有上限及停止条件。

**验收指标：** 在隔离环境先以 1/2/4/8/16/32 并发做闭环阶梯，再用固定到达率 1/2/5/10/20 请求/s 找到容量拐点；每档预热后至少 5 分钟，稳定档再跑 30 分钟。以上是测试计划，不是性能承诺。报告接收/拒绝/完成率、队列年龄、p50/p95/p99、连接池等待、线程、CPU/RSS/GC 与恢复曲线。准入以下不出现未声明拒绝；超载时队列与线程有界、拒绝可识别，恢复后能排空，不突破付费并发/预算。

**简历证据：** 可写特定机器、配置和负载下的容量拐点、排队/限流策略及前后对比。后端 worker stub 压测必须显式标记，不能用其任务/s 宣称大模型吞吐。

## 阶段 4：十万 / 百万记录、查询与存储优化

**输入：** 业务查询分布、阶段 3 的热点与慢路径。合成数据分开生成任务元数据、资料版本、会话与索引块；记录种子、长度、热租户比例、时间分布和每类实际行数。

**具体交付：** 按 1 万 → 10 万 → 100 万任务历史阶梯，先跑小档估算磁盘再扩大；不是把 100 万份完整资料塞进当前单工作区。把列表从完整报告/快照投影改为必要字段，用稳定的 `(created_at,id)` 游标分页；为工作区状态计数、领取、租约过期、历史翻页分别测执行计划后选择复合索引。`tasks` 的完整 JSON 与热元数据拆分、以不可变资料版本引用去重快照，是待验证方案；迁移后必须能重建相同快照哈希，不能以去重牺牲历史一致性。

每任务复制 200 KB 快照时，100 万任务仅这部分就约 200 GB，尚未计索引/副本；这是量级估算，不是当前实测大小。因此元数据规模实验和真实大 payload 实验分开：先做固定尺寸元数据阶梯，另做较小数量的 1/20/200 KB payload 对照，并发布实际磁盘占用。达到预设磁盘预算就停止扩量，不隐去未跑的百万档。

用 statement digest/慢日志识别耗时与扫描量，再对只读测试查询保留 `EXPLAIN ANALYZE` 的估计/实际行数、循环和耗时；它实际执行查询，不能当作纯静态解释。统计全局 `COUNT`、列表大 JSON 解码、工作区锁时长与索引写放大都要分别测。[MySQL EXPLAIN](https://dev.mysql.com/doc/refman/8.4/en/explain.html)、[Performance Schema statement events](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-statement-tables.html)。稳定排序必须补唯一键，排序字段相同的记录不能靠不确定顺序翻页。[MySQL LIMIT](https://dev.mysql.com/doc/refman/8.4/en/limit-optimization.html)。

RAG 语料扩展是另一条实验：1 千 → 1 万 → 10 万块，冻结嵌入模型/版本，比较精确检索与一种有持久化、作用域过滤的向量索引。只有内存/延迟或维护需求证明必要，再选择一个向量数据库；不同时堆多个。生成百万任务元数据不等于完成百万向量检索。

**负面测试：** 同时间戳翻页、翻页过程中插入/删除、热点租户、过期扫描与完成更新竞争、迁移中断、索引失效、磁盘接近上限、旧资料删除后历史回放。需定义游标的一致性窗口，避免承诺并发变更下无限快照一致。

**验收指标：** 每档同一查询集、冷/热缓存分别运行；记录 p95、扫描/返回行比、索引和数据大小、写入延迟、锁等待与内存。优化必须在正确性不下降下改善已识别瓶颈；保留无收益项。百万档必须有数据库行数和查询原始证据才算完成。向量档另外报告 Recall@k、索引构建耗时、搜索 p95、内存与过滤正确性。

**简历证据：** “在 N 条合成任务历史上，定位某查询瓶颈，采用某索引/游标/投影，在相同条件下将 p95 从 A 改为 B。”N/A/B 只能由实际结果填写，且不等于 N 个真实用户。

## 阶段 5：故障演练、复盘与小范围真实试用

**输入：** 阶段 2–4 的监控、身份隔离、备份方案和容量拐点。以已有真实本地死锁和复核超时作为首批案例，再做可重复的受控故障。

**具体交付：** 建立任务积压、最老任务、错误率、数据库锁等待/连接池、Redis 延迟、MQ unacked/死信、worker 与模型耗时看板；告警有触发、恢复和 runbook。Redis 延迟监控用于定位服务事件，不能拿 `redis-benchmark` 的命令吞吐代替业务吞吐。[Redis latency monitoring](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency-monitor/)、[Redis benchmarking](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/)。

每份复盘包含时间线、影响范围、关键请求 ID、证据、排除的解释、已证实根因、止损、修复、回归、防复发以及尚未知部分。做数据库备份实际恢复和结果哈希抽查；记录恢复用时及不可恢复数据窗口。灰度/回滚按快照版本和数据库迁移兼容性设计，不只保留旧 JAR。

**负面测试：** 数据库不可用/慢查询、broker/worker 重启、Redis 中断、上游 429/503/超时、磁盘压力、迟到回包、取消未确认、观测组件失败。故障注入仅操作隔离环境或明确允许的维护窗口，不人为伤害真实用户来制造事故履历。

**验收指标：** 至少完成三份不同类别复盘、一场备份恢复演练、一次回滚演练；记录发现时间、恢复时间、失败/未知用量与重复外部调用数。复盘只对已证实的原因下结论。若具备试用用户，先小范围开放并连续记录一个预先声明的观察周期，报告实际用户/任务数、反馈与故障；没有用户则如实保留为待验证。

**简历证据：** 已有真实本地故障可写“定位并修复 MySQL 锁竞争，并为 Agent 超时建立分阶段诊断与受控回归”，注入故障写“演练”。只有真实运行环境、实际影响和记录齐全，才能描述对应的线上运维经历。

## 阶段 6：短长期记忆、上下文与中断恢复

**收尾第6轮已交付切片：** 持续响应体的绝对deadline与在途取消修复完成7场景本机验收，未知用量、清理完成后确认及OS DNS限制明确保留。MySQL显式工作区共享记忆已接入Agent，绑定来源、版本与用户选择审批；没有自动总结写回、私人作用域、向量记忆检索或精确tokenizer。第7轮继续摘要/检查点/恢复；原始供应商超时根因仍未知，本机复现不能解释供应商内部行为。

**输入：** 会话版本与资料来源契约，稳定的预算/取消/任务执行链路。先做用户明确保存的项目偏好，再考虑有证据的事实记忆。

**具体交付：** MySQL 保存记忆类型、租户/工作区/用户作用域、原消息或资料版本、有效期、冲突关系、状态和删除审计；Redis 仅缓存；向量命中后重新核对权限、有效状态与来源版本。模型猜测保持候选，不能从旧回答自动升级为事实。摘要记录处理到的 turn 和版本，保留纠正/否定/未完成目标；超出上下文时按模型 tokenizer 与输出预留做有界压缩或明确结束。

检查点仅在已确认的工具边界保存，记录调用意图与结果账本。暂停/取消/崩溃/超时区别对待；外部请求已发而结果未知时先对账，不盲目重放。源资料变更后继续原快照，或显式创建新任务，不能默默混用。

**负面测试：** 跨租户泄漏、删除后缓存/向量残留、过期记忆、两份互相矛盾的资料、用户连续纠正、恶意资料要求“记住系统指令”、摘要失败、工具完成后崩溃、回包前崩溃、取消后迟到结果。

**验收指标：** 至少 12 个跨会话场景、每场景 10–20 轮，报告偏好召回 precision/recall、约束保持、错误写入、删除/过期误召回、来源可追溯率和恢复重复调用数。确定性权限/删除用例要求无越权与误召回；语义指标保留原始问题及失败，不以单一“记忆准确率”掩盖各分项。小窗口边界测试与真实模型结果分别报告。

**简历证据：** 完成后可描述作用域、来源、冲突与失效的记忆生命周期。当前会话持久化与用户固定状态不能提前写成自动长期记忆；此阶段不修改 Codex 或个人账户的记忆。

## 阶段 7：新题语义评测与工程回归门禁

**输入：** 稳定候选、旧失败回归集和来源合法的资料。网上公开问题可作为外部问题来源并逐条附链接；经过改写和配套资料加工后应标记为“公开问题改编”，不自动等于独立作者盲评。

**具体交付：** 开发集、已暴露回归与新冻结集分开；以缺信息、矛盾证据、配置/历史行为、计量单位、指代、更正、过期记忆及超时为覆盖维度。先用小规模预算试跑，再冻结至少 12 个场景、36 轮作为一批正式本地验收；场景依赖失败则后续轮标为阻塞，不冒充错误答案或跳过分母。留出未参与实现的出题/评分者，明确其是否看过实现和旧测试；AI 评分不能标成人工独立评测。

**负面测试：** 检索到无关同名资料、只检到冲突一方、引用原文存在但不支持结论、资料有基线却拒答、只有配置却断言历史运行、数字单位错、故障草稿当最终报告、修改测试 gold 迎合输出。

**验收指标：** 分别统计完整交付率、必要证据召回、结论正确性、引文蕴含、错误拒答、超时/阻塞、调用数、已知/未知 token 与任务耗时；报告样本数和逐题判定。先冻结最低验收线再跑，不能看到新题成绩后改线。对主观分歧二次复核并保留异议；系统测试全过不能覆盖语义失败。未交付题不进入已交付答案正确率，但仍进入全链路完成率分母。

**简历证据：** 可以描述评测设计、失败分类、版本和回归闭环。提升必须同集同协议对照，公开过的新题在下一轮就是回归题；不能反复调完再称独立成功率。

## 阶段 8：GPU 私有化模型服务、模型压测与端到端容量

**输入：** 用户已表示可租 GPU 且有资金预算，但未给出费用上限。本轮不租赁、不下载大模型。执行此阶段前固定最高总费用、时长、自动关机、闲置/磁盘/传输计费、保留资料与清理方式；保存账单或运行费用依据。阶段 1 的调用契约和阶段 7 的评测使模型替换有可比较的基线。

**具体交付：** 以 Linux NVIDIA 单卡 24 GB 级环境加一个许可证允许的 7B/8B 指令模型作为首个候选，固定模型 revision、tokenizer/chat template、量化方式、vLLM/CUDA/驱动与容器 digest。24 GB 是起步设备档位，不保证任意上下文和并发可装下；先核权重、KV cache 和运行开销。若证据显示显存或吞吐瓶颈，再比较 48 GB 或多卡，不先购买最大机器。接入现有 provider 适配层，先验证中文、结构化动作、工具参数、截断和错误协议，再运行真实 Agent。

推理服务放在私网/受控入口，业务服务认证、限流和请求大小限制继续生效；验证所用 vLLM 版本各端点的鉴权覆盖，不把单个 API key 当作完整部署隔离。保存部署、健康检查、重启和回滚脚本，并记录数据是否发送到外部服务。[vLLM 安装平台](https://docs.vllm.ai/en/stable/getting_started/installation/)、[vLLM 服务安全边界](https://docs.vllm.ai/en/stable/usage/security/)。

Mac 只作为可选开发验证：当前官方文档已列 Apple Silicon 的 vLLM-Metal 插件（使用 MLX/Metal，要求 macOS 15+ 与配套环境）；也可用 MLX-LM。它们不能代表 Linux CUDA 的容量、功能覆盖或性能。本机尚未安装/验证本项目模型服务，不根据 24 GiB 统一内存预报吞吐。[vLLM-Metal](https://docs.vllm.ai/projects/vllm-metal/en/stable/installation/)、[MLX-LM](https://github.com/ml-explore/mlx-lm)。

**模型压测矩阵：** 独立于业务后台，先从 512/2,048 输入 token、128/512 输出 token 与并发 1/2/4/8 起步；按显存和队列情况扩大到 8,192 输入及更高并发。固定输入/输出分布、采样参数、是否忽略 EOS、前缀缓存、冷/热启动与请求到达过程，报告实际生成长度。至少三次相同协议重复；预热不混入正式统计。共享前缀缓存与不复用前缀的负载分开，不能重复同一提示后把缓存收益写成纯推理加速。[vLLM benchmark CLI](https://docs.vllm.ai/en/stable/benchmarking/cli/)。

**负面测试：** 超上下文、过大输出、OOM、模型进程中断、队列饱和、客户端取消、结构化响应不合法、磁盘或下载失败、服务重启期间请求；只有相同配置和故障协议的实际结果，才能声称恢复表现。

**验收指标：** 客户端流式记录 TTFT、逐事件 ITL、每请求 TPOT、端到端 p50/p95/p99、请求/s、输出 token/s、错误/截断率；服务端记录排队、运行/等待请求、KV cache、显存、GPU 利用率与功耗（可采集时）。TPOT 对输出超过 1 token 的请求按 `(总耗时−TTFT)/(输出token数−1)` 计算；与 ITL 聚合口径不同。业务任务再单独测完整 Agent 交付和语义指标，不能用更短输出或更弱回答制造“提速”。[vLLM 指标定义](https://github.com/vllm-project/vllm/blob/main/docs/design/metrics.md)、[vLLM production metrics](https://docs.vllm.ai/en/stable/usage/metrics/)。

输出一个带原始数据的容量/费用表：满足预声明延迟和错误率条件的稳定请求率、实际 GPU 时长、包含失败/启动/空闲的总成本、每 1,000 个完成请求成本；另列质量通过任务比例。与托管 API 比较时明确模型并不相同，不能将差异全部归因于部署方式。若没有权限查看上游排队，保留未知，不猜测。

**简历证据：** 完成后可写指定 GPU、模型、精度、上下文、并发和延迟约束下的私有部署与压测数据；阶段 3 的后端任务吞吐与这里的模型 token/s 分别列出。通过容量测试不等于长期生产 SLA，更不证明答案可靠。
