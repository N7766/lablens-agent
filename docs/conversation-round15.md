# 第十五轮：原子批量导入、持久检索与失败链路留痕

2026-11-08，十二轮收尾的 **第 4/12 轮**。完成批量导入、持久检索、重启复用和资料版本失效的工程验证。36 次检索对照完成；单次真实 Agent 在第二次模型决策时超时，未生成报告，完整 Agent 和语义质量验收仍未完成。

## 设计与实际边界

批量导入先进入 MySQL 持久队列，单批最多 **25 份文档、100000 个文本字符**，工作区仍限制为100份／200000字符。请求携带幂等键和预期版本；申请队列容量与应用文档分别使用短事务。应用时锁定工作区，整批文档及历史版本在同一事务内写入，共用一个新 revision。取消只作用于尚未应用的批次；排队期间发生资料变更则整批失败，逐项保留原因。

默认待处理上限为每工作区4批、全局64批，导入请求落库前检查编码后大小不超过1 MiB。新的导入队列采用 **MySQL 轮询**，没有接入此前任务专用的 MQ 事件协议；本轮不声称导入经过 RabbitMQ。`APPLIED` 返回 `index_status=not_checked`，文件写入与索引可用是两个状态。

检索产物保存为 SQLite 派生数据：不可变 chunk 清单、文本位置／哈希、向量、构建状态和用量。MySQL 仍是资料与 revision 的业务事实来源。复用身份绑定快照、文档内容、切分配置及模型配置；修改或删除资料后，新 revision 不能复用旧版本索引，历史快照仍可保留。构建中／失败产物不作为可用索引，可能已经计费的失败构建不自动重试。

SQLite 默认最多128条索引记录，单产物16 MiB、数据库页上限128 MiB；满额明确拒绝，不自动清理历史产物。检索仍为**有界精确扫描**，不是 ANN，也没有完成大规模向量库吞吐验收。供应商 embedding 模型使用 `BAAI/bge-m3`；本地版本命名空间只是缓存隔离标识，`provider_revision_pinned=false`，不能称供应商权重已锁定。

## 检索评测：三种策略分别报告

另一 AI 任务在查看检索实现前编写10份 Kestrel 文档和12个问题，共1969个文本字符，每份资料恰好一个 chunk。问题包含 SFT 基线存在、配置不能证明历史行为、矛盾汇总、缺失因果证据与未知费用。它们是 **AI 编写的合成回归材料**，不是实际 DPO 排查结论、独立人工题或盲测。语料、问题、候选与有序快照在调用前冻结，运行后没有据结果改题调分。[冻结协议](evaluations/conversation-round15/protocol.md)、[快照身份](evaluations/conversation-round15/run/ordered-snapshot-freeze.json)。

| 策略 | 完成／计划 | 全部必需文档覆盖 | 两侧矛盾资料覆盖 | 宏平均 Recall@3 | 宏平均 Precision@3 |
| --- | ---: | ---: | ---: | ---: | ---: |
| BM25 | 12/12 | 12/12 | 2/2 | 1.000 | 0.444 |
| Dense | 12/12 | 12/12 | 2/2 | 1.000 | 0.444 |
| Hybrid | 12/12 | 12/12 | 2/2 | 1.000 | 0.444 |

Precision@3 的分母固定为3；本题集许多问题只有一个必需文档，按标注计算的宏平均理论上限也是0.444。三策略本次结果相同，不能据此宣称向量或混合检索优于 BM25。[逐项结果](evaluations/conversation-round15/run/retrieval-rows.json)、[汇总](evaluations/conversation-round15/run/retrieval-summary.json)。

所有36次都使用 `extractive`，没有模型生成。指标只检查所需资料进入前三名，不评价模型结论、证据状态分类、错误拒答或最终引用是否充分；单固定顺序、极小语料也不足以比较生产延迟或容量。

首次语义索引构建为 **1次 embedding 请求、10个输入、1299 tokens**。构建加本次36次检索合计 **25次请求、34个输入、1965 tokens**，已包含首次构建，不能再次相加；BM25不调用 embedding。实际 worker 重启后的独立探针另用了 **1次请求、1个输入、19 tokens**，记录 `persistent_vector_hits=10`。这两阶段合计1984个已知 embedding tokens；按冻结协议核对的标准单价估算约 US$0.00001984，属于估算而非供应商账单。索引复用仍需嵌入新问题，不能写成查询零模型调用。

## Agent：工具确实接通，报告验收失败

单独冻结一次 Agent 协议，用已公开的 SFT 基线问题验证实际链路，没有失败重试。第一次模型决策选择 `search_workspace`，工具真实调用检索接口，并在轨迹中保留索引 ID、配置 ID、资料哈希、快照与来源；返回的首条资料正是包含 SFT 基线的原文，`index_reused=true`、`index_fallback_reason=null`。这是实际模型选工具和持久检索接通的证据。

随后第二次模型决策发生 `ReadTimeout`，任务保存为 **`FAILED / agent_timeout`**，`worker_ms=60462`，`result=null`。第一次模型请求已知2410 tokens，第二次用量未知，因此整次生成用量为 `null`，不能把未知部分按0计算。没有调用 `verify_and_submit_report`，没有正式报告，最终结论正确性与错误拒答均不可评估。刷新后的 API 历史回读与终态相同，仅证明失败历史可恢复，不能宣称“刷新查看成功报告”已完成。[原始终态](evaluations/conversation-round15/run/agent-final.json)、[历史回读摘要](evaluations/conversation-round15/run/agent-summary.json)、[另一 AI 的分阶段审阅](evaluations/conversation-round15/agent-review.md)。

第二决策开始时总剩余预算约54.598秒，扣除20秒复核保留后，请求期限约34.598秒；客户端记录请求耗时约35.045秒。故本次是**请求读取期限触发**，不是80秒总预算全部耗尽。现有资料没有供应商排队、首字节或逐段读取计时，尚不能确认供应商内部根因；工具阶段14.931ms也是单次小快照观察值，不是性能分位数。

## 过程中的难题与修正

- **未知提交与前端竞态：** 发送后断连时保留原请求及幂等键，用户明确重试才重发；已有旧批次回执不能掩盖新的未知提交。工作区 A→B→A 也会使旧响应失效，读取版本期间切换工作区不会继续提交。刷新只读，不暗中导入或构建。相关反例进入UI测试。
- **队首坏批次阻塞后续任务：** 初版永久 SQL 约束失败会反复轮询同一批次。修正为应用事务先回滚，再以新事务记录逐项失败；取消或其他执行已先完成时不覆盖终态。故障测试使用真实历史主键冲突，不提高数据库权限；临时数据库故障继续保留排队。
- **检索成功不等于持久索引证据完整：** 在付费运行前补齐 Agent 工具输出的索引来源字段并重新冻结候选，使报告轨迹可以核对具体索引，而不只知道资料片段存在。旧冻结记录保留。此次真实调用确实复用了索引，但模型报告依旧失败，两个结论分别记录。
- **超时需要按阶段解释：** 区分请求次数、已知 tokens、未知消费、请求期限与总预算，保留失败原件；没有通过追加调用、放宽门槛或把检索分数当作语义分数来修饰结果。
