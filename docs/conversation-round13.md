# 第十三轮 / 收尾 2：持续负载与资源诊断

2026-11-08。增加 Hikari、Tomcat、执行队列和 MySQL 准入事务的资源观测，延长固定合成负载；同时运行一次严格限额的真实模型探针。候选实现 `55cf2be`，未合并或升级主服务。本轮后端验证和模型验收分开记录，十二轮计划不会因工程测试通过而自动将模型语义标为完成。

## 为什么增加这些指标

上一轮验收把全局活动任务上限设为 12（产品默认 1000），但队列上限本身不能说明系统在等数据库连接、全局 guard 锁还是执行 worker。现在分别记录连接池 active/pending/获取耗时、HTTP busy 线程、三类 executor 占用和固定预算，以及准入 guard SQL 耗时和事务实际完成耗时。

资源状态从 Hikari MXBean 读取，不额外借连接；整个原有 `/api/system/status` 仍会查询数据库，不能说这个端点在数据库故障时完全无阻塞。guard timer 包括 SQL 往返，事务 timer 从 callback 到真实提交/回滚，不含之前 Redis 判断或获取连接。指标的含义见[协议](evaluations/conversation-round13/load-protocol.md)。

保留 Hikari 连接上限 12、3000 ms 获取超时、Tomcat 线程上限 200 和 2 个业务 worker；配置可以调整，但本轮没有通过增加资源掩盖瓶颈。真实数据库测试刻意占有 guard 和耗尽独立连接池，验证等待能够被观察到；无等待负载本身不能证明诊断有效。

## 持续负载：保留一次未通过的验收

**严格验收未通过。** 第 3237 个预定槽位（323.8 秒）迟到 111.089 ms，超过冻结的 100 ms 门槛，因此没有发送。全部 4320 槽位仍在账本中，17/18 项核心检查通过；资源检查 15/16，唯一失败是继承核心验收失败。不能以 1,595 个成功任务覆盖漏发，不能重新跑一遍挑成功结果，也不能把该客户端迟到称作服务端超时。迟到根因尚未确认。

最终任务排空，恢复阶段最后 90 秒受理 180/180；请求 ID、持久任务与 worker 开始/完成逐项核对见[开发复核](evaluations/conversation-round13/evidence-review.md)。[原始汇总](evaluations/conversation-round13/load-candidate/summary.json)、[资源与每分钟结果](evaluations/conversation-round13/load-candidate/resource-summary.json)、[资源分析](evaluations/conversation-round13/resource-review.md)保留完整失败。

现有样本没有连接池或 HTTP 线程饱和的证据；两 worker 加固定等待能解释过载时的业务积压，暂不扩大池子。采样不能保证所有瞬间，且观察器也增加负载。timer 累计量不等于分位数；heap 不等于 RSS，9 分钟不证明无泄漏或多日稳定。与上一轮时长和仪表不同，不能据延迟差异宣称因果提速。提交响应分位数包含大量拒绝；任务时延只属于已受理集合。

## 模型诊断：可达，不等于可交付

冻结方案最多 3 次顺序请求、无重试：极小请求后才允许生产 RAG 生成和复核。实际只执行一次：DeepInfra 返回 HTTP 200，完整调用约 1048 ms，用量为 13 个输入、3 个输出 token。输出是 `OK.`，与事先固定的 `OK` 不符，运行器按原规则停止。

因此本轮没有 RAG 报告、没有 live 语义评分，也没有完整 Agent 或刷新后历史验收。离线检索覆盖 4/4 只说明所需资料进入冻结检索结果。该题由另一 AI 开发代理依据官方资料改编，不是独立人工评测。[原始响应、用量与复核](evaluations/conversation-round13/model/review.md)。

本次暴露的是实验设计问题：把标点精确匹配作为后续传输诊断的门槛，会在已经得到有效响应时阻断更有意义的诊断。下一轮应在运行前将传输门和指令遵循评分分开。本轮不删除 claim、不放宽原门槛、不补用剩余额度，也不把旧四次大请求超时宣布解决。

## 实现验证和难题

Python 全量 **1,838 通过**；最终 Java **141 项发现、139 通过、2 条条件重启用例跳过**。Java 首次 138 项通过后，复核发现新增队列容量指标的竞态并修复，再执行完整矩阵。已有真实 MySQL/Redis/RabbitMQ 普通集成均启用；本地两条跳过项不计为 broker 重启通过。[回归证据](evaluations/conversation-round13/README.md)。

- 固定队列容量不能实时用 `size()+remainingCapacity()` 相加：两次读取之间任务可能被取走，导致容量 1 报成 2。改为使用构造配置，加入确定性交错回归。修复的是观测正确性，未改变实际队列大小。
- timeout counter 不能只核对首尾为零：补充全部样本检查与 0→1→0 负例。离散采样仍不能证明所有瞬间都无异常。
- 阶段、请求和外层执行耗时存在包含关系，不能求和。HTTPX 返回完整响应的时间不是首字节时间；新增 connect/read/write/pool 分类只描述客户端异常阶段，不直接说明历史网络或供应商根因。
- 请求遥测故障尽力隔离，不能覆盖原业务结果；这一保障针对 request observer，未声称所有 stage recorder 都具备故障隔离。

完整记录见[执行过程](evaluations/conversation-round13/execution-notes.md)。下一轮为[历史数据分级扩量与查询优化](evaluations/conversation-round13/next-round-handoff.md)，模型诊断缺口继续独立跟踪。
