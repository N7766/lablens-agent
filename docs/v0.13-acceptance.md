## 1. 一次可复核的真实 DPO 排查

[完整案例](cases/dpo-preference-generation.md)和[离线证据包](../evaluation/cases/dpo/README.md)包含18份来源、28个带原行号片段、15条结论映射。`python scripts/verify_dpo_case.py --self-test` 可在无API/GPU条件下重算964条保存输出；对源档案的18个文件哈希也已只读核对。

- Stage 4训练首尾偏好准确率0.55625→1.0，偏好验证两次均1.0；不能说验证准确率持续上涨。
- SFT自由生成439/462=95.02%，full DPO为153/462=33.12%。已有SFT基线；两者是不同初始化路线，不能说同一SFT权重继续DPO后退化。
- 基座40题13/40，DPO相同ID12/40，且batch不同；这反驳了简单归因，但不是严格受控实验。
- YAML写`max_prompt_length: 512`，历史日志却明确忽略该键。这是配置不等于生效参数的实际反例。
- `output_tokens`实际按`len(prediction.split())`计数，不能写成tokenizer token或时延。
- 排除的是存档汇总/当前规则复算不一致；过拟合、生成预算、提示协议、权重和数值问题仍未获唯一归因。

工具作用可演示为：定位报告/配置/日志→检索原文→核对来源与片段→用离线脚本复算→逐结论标支持、矛盾或不足。案例由AI协助整理、另一个AI复核，不伪称外部专家认证。

## 2. 修复后的生成仍有哪些问题

模型现在选择稳定的证据片段ID，服务端填入原文，避免复制引号/换行破坏引用。输出按命题记录三种判定，并区分资料事实、配置、历史观察、因果判断。模型初稿后由同一模型另做一次复核；这既非独立评委，也不保证改善答案。

## 3. 已接通的 Agent 链路

浏览器→Spring Boot任务API→MySQL不可变快照→现有Python `Agent.run`工作区分支→模型选择`search_workspace`→本机真实HTTP检索→`verify_sources`核对原文/偏移/哈希→`submit_report`→同模型复核→JVM保存报告/失败轨迹→刷新读历史。

检索请求中的资料与版本由服务绑定，模型不能选任意URL。全部检索到的片段须核验，包括反证。零命中可结束为不足，空核验明确表示没有来源被核验。最多6次决策、8次工具、1次复核，总预算75秒；超时明确停止，不保证取消已经到达供应商的请求。

[浏览器实测记录](evaluations/v0.13/agent-browser/README.md)保留5次真实尝试：3次得到报告、2次失败。首次缺证据遇到空核验协议冲突，已修；另一条真实请求超时，随后经界面手动创建新任务成功，没有删除失败或自动重试。最终可展示SFT95.02%和缺失p99的不足结论，刷新与编辑资料后旧快照仍保留。

版本许可在数据库事务锁内核对；旧许可409拒绝且未创建任务，新确认才提交；相同幂等键仍回到原任务。Agent报告不走结果缓存。未知provider用量为`null`，不伪写0。

[真实受控故障验证](evaluations/v0.13/agent-fault/README.md)：JVM/Python/MySQL/Redis均真实运行，只有provider为回环受控服务；决策超时、embedding工具超时2/2场景及35/35断言通过，0外部模型调用。刷新、幂等重放和直接SQL核对一致。
