## 一轮改动怎样留下记录

1. **Issue**：写可复现现象、证据链接、影响范围和验收条件；已有问题补充进展，避免重复开单。
2. **PR**：一个清楚的改动对应一个分支，说明行为变化、实际验证与未完成项；只有完整解决的 Issue 使用 `Closes`。
3. **检查与合并**：确认 diff、必要回归与 CI；纯文档改动检查链接、命令入口及指标来源。
4. **结果**：把实际结果和失败补回 Issue，关联合并提交；满足已定义验收后再归档。Release 对应可交付版本，不要求每个 PR 发版。

模板与命令见[贡献指南](../CONTRIBUTING.md)。不做空提交、倒填历史、虚构用户反馈或自动刷活跃；这类记录不能说明项目在持续改进。

## 评测与材料边界

- 问题、资料、评分规则和预算在运行前冻结；已公开题后续作为回归，不再称未见题。保留首次失败、超时、依赖阻塞和未知用量。
- 工程测试、检索命中、引文存在、报告交付、语义正确各自统计。AI 评分标明作者/评分者关系，不写成人工独立评测。
- 运行代码与模型效果分别验收；本地故障演练和合成压测不写成商业线上流量或生产事故经验。
- API 与 GPU 实验先确定资料发送范围、调用/费用上限和停止条件。租赁另核计费、自动关机与存储清理。
- 公开提交不包含密钥、私有原文、完整数据库、模型权重或未授权数据。原始历史评测不因新版本改写。
