复查人：本轮负责本地 HTTP 超时诊断的 AI 子代理，未实现 Java 认证、Python 服务身份或浏览器认证代码。此记录是一次普通源码正确性复查；不是人工独立验收、完整安全审计或公网部署批准。主代理的完整测试、集成测试和浏览器证据须单独读取。

## 发现及处理

### 1. 多标签页切换身份后可能保留旧项目内容

首次检查的 `static/auth.js` 仅在本页登录/过期时清理状态。另一标签页登录新账号会替换共用 Cookie，但本页仍持有旧 `session`、权限角色和报告 DOM。旧项目对新账号返回 404 时，旧实现也不会清理（只处理 401/403）。这一问题涉及浏览器身份一致性，不意味着服务器跨工作区 ACL 已被绕过。

已确认修复：`AuthFilter` 给已认证响应添加 `X-LabLens-User-Id`；浏览器检查响应身份不符，以及工作区的 403/404，触发清理和重载。`auth.js` 同时监听 `localStorage` 身份变化，立即隐藏工作区、清理状态，并在 `fetch` 前后检查失效状态。

复查状态：**已回读并通过定向浏览器逻辑测试**。复查者补充了真正延迟完成 `fetch` 的测试：先发送旧身份请求，随后触发另一个标签页的身份变化，最后释放旧请求的 200 响应；请求被拒绝，下游报告消费者没有执行。不是仅在切换身份后再发送一个新请求。`node --test services/workspace/tests/auth-ui.test.cjs` 共 11 项通过、0 失败。该测试使用真实前端源码的 Node VM/模拟 DOM，不冒充真实浏览器多标签端到端验收。

### 2. 取消成员权限与已经授权请求的并发边界

`AuthFilter` 在控制器执行前完成成员校验；`WorkspaceStore.putDocument` 等业务事务稍后获取工作区行锁，并不再次校验成员。因此一个已经通过校验、正在等待锁的请求，可能在撤权提交之后才完成。这是客观存在的时序，不支持“撤权立即中断一切在途操作”的描述。

本轮明确采用 **请求开始时授权** 的契约：只有在撤权提交后才进行 ACL 校验的新请求保证被拒绝；此前已授权的在途请求、已受理任务或导入可以继续。撤权不撤回已经复制的材料、取消已受理模型消费或作废已发往服务端的操作。此语义作为受控本地候选版本的已接受限制，不把它写成原子撤销能力。

成员管理本身已有更强边界：`AuthStore.setMember` 在工作区行锁内再次检查操作人的 OWNER 权限，且禁止修改/删除 OWNER；`adopt` 在同一行锁内检查零成员后才创建所有者，不能通过并发收养取得已拥有工作区。未发现超出上述已授权在途请求范围的权限提升路径。

处理状态：**契约已明确，保留限制，不声称已改为事务内即时撤权**。
