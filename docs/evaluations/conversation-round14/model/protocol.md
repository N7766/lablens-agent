# Round 14 model probe: separate transport and exact-output checks

Date: 2026-11-08. This new experiment is a direct BM25/live RAG diagnostic. It does not execute Agent tool selection, JVM task history, long-term memory or private GPU serving. Round 13's `OK.` exact-output failure and Round 10's timeouts remain unchanged. A new once-only identity is declared before any call; no old claim is resumed.

## Frozen sequence and independent checks

- Provider/model remain `https://api.deepinfra.com/v1/openai` / `Qwen/Qwen3-235B-A22B-Instruct-2507`. No fallback, retry, embeddings, proxy changes or main service changes.
- At most 3 POSTs: tiny completion (`Reply with exactly OK.`, temperature 0, max_tokens 64, <=10 seconds); then the one new fixture through real `answer_rag`, using the production prompt, schema, generation, review and final validators. Generation <=35 seconds and review <=40 seconds, each max_tokens 2600 and temperature 0. The planned review is not an extra repair attempt. Any fourth request is blocked before transport.
- **Transport gate:** the tiny request must return a complete successful HTTP response, a parseable completion object with an assistant message, `finish_reason=stop`, nonempty string content, known provider usage and an unexpired request/overall budget. Failure blocks dependent RAG. This gate does not require the content to equal `OK`.
- **Exact-output instruction check:** independently record whether stripped content equals `OK`. For example, `OK.` is an exact-match failure but can satisfy the transport gate and permit the already planned RAG requests. Empty/non-string content, invalid completion structure, unknown usage or incomplete generation still blocks. This change is specified before the new run; it does not rescore Round 13.
- Stop before any next call on earlier provider failure or unknown usage, source/payload drift, cost/preflight failure, user interruption, max request count or the monotonic 100-second start deadline. A response after its request budget is not a pass even if usage is known. HTTPX phase timeouts and the total start deadline do not guarantee hard real-time interruption of a call already in progress. No automatic resume after failure or interruption.

## Freeze, budget and safety

Before live execution, commit this runner, all `lablens/*.py`, fixture, rubric, protocol and operator-verified pricing file. Freeze HEAD, source inventory/hash, experiment hashes, Python/HTTPX/Pydantic versions, endpoint/model, tiny and generation payloads, local retrieval, gate definitions and budgets in `plan.json`. Keep HEAD unchanged between freeze and run. Dynamic review content cannot be known before the generated draft; its production builder and fixed schema/budgets are frozen, then its actual request is stored and hashed before its only send.

The [official DeepInfra model page](https://deepinfra.com/Qwen/Qwen3-235B-A22B-Instruct-2507), rechecked by the root operator on 2026-11-08, lists context 262144, standard input/output $0.09/$0.55 per million tokens and priority $0.135/$0.825. Use the higher priority rates to reserve the entire context input allowance for each of three possible calls plus output maxima 64/2600/2600. The conservative planning bound is **US$0.11051112**, below the **US$1** ceiling. It is not measured consumption or a billing receipt. Payloads are limited to 128 KiB, independently of tokens; bytes are never called a model token estimate. An accepted request is bounded by declared provider context; invalid context responses must not be retried.

Exact endpoint/model and credential presence must pass preflight before consuming the claim. The runner suppresses `.env` loading, reads the explicitly supplied environment, records only booleans for proxy environment configuration and `trust_env=true`, and never saves keys, request headers, proxy URLs or environment dumps. It does not change proxy routing or service tier.

`run/once-only-claim.json` is created exclusively and fsynced before any POST. Request intents are written/fsynced before transport. An unresolved intent is not proof that the provider accepted the request. Any unfinished run is preserved; never delete a claim to gain another attempt. SIGKILL/power loss can prevent final sealing and leaves the outcome incomplete, not permission to resume.

## Evidence and scoring

Retain actual request JSON, canonical/wire-body SHA and byte count, raw provider response bytes before parsing, status, safe exception class chains, actual transport timeout, production telemetry, known/unknown usage, separate tiny transport/exact-output decisions, retrieval/report/failure and a final inventory/hash seal. Transport exception messages are not published because they may contain credentials. Recording errors must not replace an already active original exception; no observer failure should trigger another request.

The wrapper clamps the actual timeout after the production observer starts, so `request-intent.json.timeout_seconds` is the actual transport allowance and trace `timeout_ms` may be larger. Do not equate these or sum durations of nested stages. `response_received` means a complete HTTPX Response was observed; its absence does not establish that no headers or bytes arrived. Missing usage remains unknown/null, never zero cost. Tiny and RAG usage are separate; aggregate only when every attempted request reports known usage.

After sealing, score [retrieval and semantics](semantic-checklist.md) separately. The [new fixture](fixture.json) is an AI-authored synthetic sample inspired by a verified primary MySQL source. It is not an actual incident, an independent human evaluation or a stable-quality benchmark. Exact-output success, HTTP 200, schema validity, retrieval coverage and quote membership each have narrower meanings than final semantic correctness. The new fixture must not be used to tune production prompts or validators before its first run.
