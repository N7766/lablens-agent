# Round 10：复核协议的有界诊断

本轮针对 Round 9 两个 HTTP 200 后未能交付报告的已暴露失败场景，定位当前响应与验证器之间的实际失败，不重写旧分数。旧响应没有留存，不能用新响应反推历史根因。

## 运行前约束

- 仅 `cedar-t1`、`harbor-t1` 原草稿的直接 `review_assessments` 请求；资料、草稿、上下文及历史请求重建写入 `inputs.json`，记录来源和 SHA。无新检索、embedding、Agent 决策或数据库任务。
- 两阶段各最多两次，共最多四次调用：`baseline` 使用原提示和当前诊断代码；封存 baseline 后，若有明确、通用的修复依据，提交最小补丁后运行 `repaired`。不追加抽样，不自动重试或恢复中断的阶段。不以成功为停止条件选择结果。
- DeepInfra `Qwen/Qwen3-235B-A22B-Instruct-2507`，temperature=0，max_tokens=2600，唯一端点 `https://api.deepinfra.com/v1/openai/chat/completions`。不租 GPU，不调整模型或输出预算来追分。
- 使用原复核剩余时长：Cedar 39,968.432 ms，Harbor 35,098.544 ms。准备和校验时间不计入这段直接复核预算；这不等于完整 Agent 在 75 秒内成功。
- 每阶段先提交源码及实验文件，再冻结候选 commit、全部 Python 模块/执行脚本哈希、输入/协议哈希。baseline 必须在调用前确认当前请求与历史源码重建请求对象相等。repaired 固定同一输入且引用 baseline raw seal。
- 运行器的持久 once-only claim 防止重复阶段。任何失败或中断消费该阶段，不删除 claim 重跑。第二阶段若没有合理补丁可以不执行；未调用记为未调用。

## 观察与判定

保存每次实际请求、原始 HTTP response bytes（在生产超时和解析判断之前）、HTTP 状态、usage、provider 请求轨迹、生产 observer、验证诊断和最终返回结果/错误。凭证只从本地环境读取，不存储请求头。原始产物先封存再作分析。

依次区分：传输是否返回、是否在截止时间内、JSON/finish_reason、ID 分区恢复、最终证据校验、最终语义。HTTP 200、schema 合法、原文存在分别都不能替代后续判定。失败语义为 `not_evaluable`。对成功返回按运行前 [语义清单](semantic-checklist.md) 核查计算、严格边界、AND 条件、未知信息和逐行引用蕴含；这是 AI 开发回归，不是人工独立盲测。

候选修复不能削弱重复/遗漏/重叠 ID、错误来源、因果断言、数值/作用域绑定等验证器。若实测不能证明提示冲突是根因，则只将它记录为已证实的提示缺陷和修复假设，不称历史失败已解决。一个场景一次调用不建立稳定成功率、统计显著收益或模型普遍能力。

## 发布边界

保留两阶段原始记录、失败、token 已知/未知值、耗时和源码身份。既有 Round 9 raw/gold/评分保持原样。改动进行离线回归和必要工程检查，再同步 GitHub 草稿 PR、真实问题进展、工程日志和桌面说明。没有完整 Agent 重验前，不宣称多轮链路、生产流量、答案质量或上线验收已通过。
