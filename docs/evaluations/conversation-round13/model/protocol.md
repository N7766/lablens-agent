Date: 2026-11-08. This is a direct RAG diagnostic, separate from sustained backend load. It does not execute Agent tool selection, JVM history persistence, multi-turn memory or private GPU deployment. Historical Round 10 failures remain unchanged.

## Fixed sequence and stopping rules

- Exact provider: `https://api.deepinfra.com/v1/openai`, model `Qwen/Qwen3-235B-A22B-Instruct-2507`. No fallback, retries, embeddings, proxy changes or service changes.
- At most three POSTs, strictly sequential: one tiny completion (`Reply with exactly OK.`, temperature 0, max_tokens 64, timeout <=10 seconds), then one fresh fixture through the real `answer_rag` BM25/live pipeline. That pipeline uses the production generation and review builders and validators; each has at most one POST, max_tokens 2600, temperature 0. Generation timeout <=35 seconds and review <=40 seconds. The runner limits the existing call's timeout; it does not alter the model prompt, schema, evidence or returned answer.
- Stop on tiny failure, incomplete output or unknown usage. Stop before the next POST when any preceding POST failed or usage is unknown, the total monotonic 100-second start budget is exhausted, the request count reaches three, cancellation occurs, source identity changes, or cost/payload preflight fails. A failed generation blocks review. Never delete or resume a once-only claim. These HTTPX timeouts and the start deadline are not a hard real-time guarantee for a currently running call.
- A generation that parses to JSON but is not a conforming selection report is not repaired by an extra request. The production review remains the one planned second stage, not a retry. Any extra fourth call is rejected before transport.

## Freeze and cost gate

Before live execution, commit all `lablens/*.py`, this runner, fixture, rubric, protocol and pricing file; freeze their hashes, HEAD, Python/HTTPX versions, endpoint/model, tiny and generation payloads, retrieval result and budgets in `plan.json`. Review content necessarily depends on the not-yet-returned generation; freeze its production builder source and fixed schema/budget rules, then save and hash the actual review request before its only send. Never claim its content was known before generation.

The [official model page](https://deepinfra.com/Qwen/Qwen3-235B-A22B-Instruct-2507), checked 2026-11-08, advertises a 262144-token context. The root operator supplies verified `pricing.json`; use the highest declared priority rates (input $0.135/M, output $0.825/M) as the conservative cost coefficients. Charge an entire context of input for each possible call plus its maximum output, without claiming JSON bytes are model tokens. The three-call upper bound is $0.11051112, below the $1 ceiling. This deliberately overcounts input capacity and is a planning bound, not actual billed cost. The gate also bounds each serialized body to 128 KiB and max output to the frozen value; an accepted valid request cannot consume more input tokens than the provider's declared context. Context-invalid requests may fail and must not be retried.

Credential presence and exact endpoint/model are checked before claiming. Only booleans for HTTP_PROXY/HTTPS_PROXY/ALL_PROXY/NO_PROXY (upper/lower case) and `trust_env=true` are saved, never proxy URLs, keys, headers or environment dumps. `load_dotenv` is disabled in the runner's child process so a hidden .env cannot change the verified explicit configuration.

The persistent `run/once-only-claim.json` is created exclusively and fsynced before any POST. Every request intent is written and fsynced before transport; intent means an attempt may have been sent, not proof of provider acceptance. For an interrupted process, retain all existing evidence and treat unresolved intents/usage as unknown. SIGKILL/power loss may prevent the final seal; that is an incomplete run, never permission to resume.

## Evidence and interpretation

Persist raw HTTP response bytes before parsing/validation; actual request JSON/body SHA/bytes; safe timeout/exception type; HTTP status; observed elapsed times; known or unknown provider usage; production telemetry; local retrieval; production final report or failure; and a final file-inventory/hash seal. The transport wrapper applies the 35/40-second stage ceiling after the production observer starts: `request-intent.json.timeout_seconds` is the actual transport timeout, while production trace `timeout_ms` can describe the larger configured allowance. Do not report those as identical. Exception messages are not dumped because transport errors can include credentials or proxy URLs. Production sanitized RAG errors and exception class chains are retained; original exceptions still propagate rather than being overwritten by diagnostic errors. No response object means only no complete Response object was returned, not proof that headers or bytes never arrived.

An instrumentation write failure stops further calls; where a transport exception already exists, recording failure must not replace it. Save the original failed result, not a later successful retry. Usage from tiny and RAG is reported separately and together only when each is known. Missing usage remains null/unknown, never zero cost. Phase timings are not added to containing total timings.

After sealing, evaluate retrieval and [semantic obligations](semantic-checklist.md) separately. It is one new-sample preacceptance check, not independent human evaluation or a quality benchmark. A returned report is not semantic success.
