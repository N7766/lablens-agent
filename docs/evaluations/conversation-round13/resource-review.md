目前没有证据支持扩大 Hikari 或 HTTP 线程池。更符合记录的解释是：**两个带固定 400 ms 延迟的受控 worker 限制了消化速率，MySQL 中的活动任务达到 12 后拒绝新任务**。这一解释针对本次实验配置，不是实际 LLM 服务的最大容量结论。guard SQL 的均值较小且连接池没有可见积压，未显示它们在这次 20 req/s 小资料负载中成为主要限制；不能据此排除更高提交并发、大文档快照或大量历史记录下的全局 guard 热点。

## Timer 的正确分母与范围

完整准入计时采用 `summary.json` 中 `system_before.process_metrics` 与 `system_after.process_metrics` 的差值，而不是把周期采样最后一次当作全程结束。前者所有准入计时初值为零，后者恰好包含全部 4,319 个已发送请求：

| 计时器 | 次数差值 | 累积秒数差值 | 区间均值 |
| --- | ---: | ---: | ---: |
| guard SQL，`result=acquired` | 4,319 | 1.529205488 | 0.354065 ms |
| 提交事务，`completion=committed` | 1,595 | 7.319073741 | 4.588761 ms |
| 提交事务，`completion=rolled_back` | 2,724 | 5.852305229 | 2.148423 ms |
| 提交事务，以上两类合计 | 4,319 | 13.171378970 | 3.049636 ms |

公式为 `1000 × Δ累计秒数 / Δ次数`。guard error 和 transaction unknown 次数均为零。回滚计时包含容量拒绝，是预期背压路径，不应全部计为数据库故障。guard timer 包括 SQL 往返和取锁时间，不是纯服务端锁等待；事务 timer 包含 guard，不可与 guard 再相加。事务计时不含此前 Redis 和连接获取，不能用它直接替代 HTTP 响应时间。

Hikari 没有同样的完整首尾状态计数，使用 106 次 Actuator 中首次与末次采样的差值：采样批次起点约为 0.000035 秒至 536.895420 秒，获取连接次数 `31,643 − 208 = 31,435`，累计时间 `0.181 − 0.015 = 0.166` 秒，导出区间均值约 **0.005281 ms**。每个批次内部按顺序抓取，具体指标抓取稍晚于批次起点。该值受导出精度影响，并涵盖任务、状态观察器等全部数据源活动，不能写成单次业务提交数据库耗时。

同一 Actuator 首尾区间只覆盖 4,312 次准入计时增量，不能以该分母代表全部 4,319 个请求。它得到 guard 均值 0.354086 ms、事务均值 3.045819 ms，与上表的完整区间口径不同。周期样本中 Hikari acquire 的窗口 MAX 最大为 12 ms，guard 为 11.611833 ms，事务为 16.702583 ms；这些是 **Micrometer 时间窗口最大值的采样**，不是精确全程最大值。上述计数和总时长均不能推导 p95/p99。

## 分钟变化

以下受理、拒绝、未发和 HTTP p95 来自资源汇总；完成数按逐任务 `finished_at` 减去本机 `load_started_at_utc` 分桶。完成数与受理数可以跨分钟错开，尤其是过载积压转入恢复阶段。

| 分钟 | 到达率 | 受理 / 拒绝 / 未发 | 本分钟完成 | 提交 HTTP p95 | 全局活动数采样最大 |

过载三个完整分钟各完成 288 个任务，即该窗口内 4.8 个/s；worker 耗时中位数为 410 ms，两个执行槽的简单服务时间估算约为 `2 / 0.410 ≈ 4.88 个/s`。两者接近，支持受控 worker 消化速率主导积压的解释，但不构成最大吞吐测量。第 4 分钟受理数较多包含填充空队列的阶段；第 7 分钟完成数多于新受理数是前一阶段积压继续完成，不能误计成额外受理。

过载阶段提交 p95 降低主要伴随快速拒绝占比提高，不能当成成功业务变快。第 6 分钟仍有一次 164.823 ms 的提交响应，发生于预定 325.3 秒的请求，和 323.8 秒的未发槽位不是同一请求。现有离散 CPU/线程/连接指标没有定位两者根因；不能据此断言是数据库、GC、网络或客户端事件循环问题。

## 内存与后续判断

`area:heap` 使用量的 106 次采样范围为 36,724,432–112,616,280 bytes，即约 **35.02–107.40 MiB**；首次 84.78 MiB、末次 72.02 MiB。配置 `-Xmx512m`，heap max 聚合读数约 512 MiB。未限定 area 的 `jvm.memory.used/max` 混合堆和非堆，不能拿来计算堆利用率或冒充进程 RSS。

这九分钟没有观察到持续升高的堆使用曲线，但最后一个值低于第一个值也不能证明无泄漏。没有堆转储、存活对象归因、RSS 或多小时稳定性证据；本轮不作“无内存泄漏”结论。

下一步保留现有资源预算，在新的冻结实验中检查调度迟到与大数据量查询成本；若要改善吞吐，先做单一变量、同负载同采样口径的对照。改变 worker 数量、资料规模、接受标准或客户端调度规则都应建立新的实验身份。当前 1 次 unsent 与 `passed=false` 应永久保留；不能用另一个成功重跑覆盖本次失败。
