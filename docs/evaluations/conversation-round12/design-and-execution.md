## 为什么把容量控制放在数据库

进程内 semaphore 只能约束单个 JVM 的执行并发，单工作区的 pending 上限也不能限制多个工作区累积的总量。任务已经由 MySQL 持久化，容量权威继续放在数据库：新提交以 `READ_COMMITTED` 开启事务，依次锁全局 singleton guard、工作区、会话，然后查询活动任务并提交任务/outbox。活动包括 QUEUED、RUNNING 和 CANCEL_REQUESTED；取消请求尚未完成时继续占容量。

不引入另一个需要释放、过期和对账的 Redis 容量计数器。MySQL 的索引查询以 cap 限制扫描结果，guard 让新任务串行检查。终态只释放容量，不存在将终态重新激活的旁路。提交成功指标在 afterCommit 中增加，避免回滚也计为受理。代价是 guard 成为共享热点；本轮验证正确性和短窗背压，不证明它能承担任意提交速率。持续负载、连接池等待和数据规模另列收尾 2–3 轮。

跨 JVM 约束依赖所有共享数据库的实例采用相同 cap，且所有新任务走此提交入口。正常 HTTP 请求先查已提交幂等键，随后执行 Redis 判断，再进入上述事务；不持全局锁等待 Redis。内部调用若已有事务，必须是 READ_COMMITTED 且不得预持资源锁；不能笼统说所有调用场景都在事务外执行 Redis。

## 幂等与 Redis 故障

已提交同键同内容直接返回原任务；同键不同内容仍为冲突。两个请求在第一次提交前同时进入时，Redis 记录的是新提交尝试次数，可能消耗两个 attempt；最终数据库只保存一条任务。Redis 拒绝或不可用后再检查已提交幂等键，覆盖并发赢家刚完成的窗口。全局容量拒绝也可能已消耗本次 attempt，不称精确的付费额度预留或结算。

Redis 决策区分 ALLOWED、LIMITED 和 UNAVAILABLE。启用速率门时，不可用会拒绝新的模型或 embedding 请求；BM25/extractive 仍可通过数据库容量门。缓存故障继续视为 miss。`LABLENS_RATE_LIMIT<=0` 是显式关闭速率门，不提供 Redis 故障拒绝保障。新增四种暂时性错误携带 Retry-After，客户端应保持幂等键、有限退避，不立即无限重试。

## 实际执行问题

原环境把 Maven 和 Redis 二进制放在已被清理的 `/tmp/lablens-tooling`，原 Redis 进程仍运行但路径无法用于新实验。先创建的隔离数据库和 broker 已保留；启动 Redis 步骤失败后只补齐缺失工具，未重新初始化已有环境。Maven 3.9.16 从 Apache 获取并校验官方 SHA-512；Redis 8.2.2 从官方源包编译并记录下载 SHA-256（不把自行计算摘要称为独立校验）。工具放入忽略的 `.local/tooling`，本轮用 Redis 6383、RabbitMQ 5674、JVM 8086 和 worker 8770，未替换主服务。

首次完整 Java verify 成功：135 项发现、133 通过、2 项条件重启用例跳过、无失败/错误。原有 outbox 回滚测试显式使用 RC，1000 事件 MQ 测试单独设 global cap 2000，避免把新增产品默认限额误当消息可靠性故障。本轮的并发测试覆盖 16 个提交争用 4 个全局槽位、工作区限额、RUNNING/CANCEL_REQUESTED、回滚释放、慢 Redis 与幂等竞争等。

正式压力脚本和协议在运行前冻结；无隐藏重试或覆盖失败目录。运行器的 HTTPX 5 秒为各 I/O 阶段超时配置，不是 5 秒总墙钟 SLA。计数检查只作为入口，最终复核还要把 accepted task ID、worker 开始/结束以及数据库终态逐项对账，不能仅凭相等的总数断言逐任务一次执行。采样 high-water 也不等于连续峰值。

Redis 故障脚本首次在进程预检阶段拒绝执行：隔离 Redis 的 PID 文件原由启动器记录，配置里没有显式 `pidfile`。此时没有 POST、没有发送停止信号，记录保存在 `redis-outage-preflight-failed/`。补齐同一个绝对 PID 文件配置后，另建实验目录执行；未修改验收脚本、业务代码或两组已封存的压力结果。成功记录通过 PID 文件、ps 与 Redis INFO 的 PID/port/config_file 核验对象，观察旧进程退出和端口关闭，再启动新 PID。新目录的全部四个 POST 与失败预检分别保存。

两个运行器合计 29 项本地单测通过；故障运行器的假对象测试覆盖拒绝错误目标、恢复失败、异常与中断后恢复。真实故障的 41 个检查项包含 GET 成功等观察器检查，不能写成 41 种独立故障。实际业务场景是 provider 拒绝、旧键重放、停机时离线任务与恢复后离线任务。

模型诊断只读取旧封存资料。四次旧 timeout 继续保留，未得到完整 Response 不等于未收到任何响应字节；具体超时类型和代理因果均未知。本轮没有模型、embedding 或 GPU 调用，下一步见[有界诊断设计](model-diagnostic-next-step.md)。
