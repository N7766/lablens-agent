# Round 8：执行过程、难题与证据边界

2026-10-31。候选 `141a9186dbd187a4621d78169f212c67c78eeb87`，`workspace-agent-v9`。本轮把修复、工程验收、一次真实采集和语义评分分开；没有重新训练或租用 GPU。

## 改动为什么这样做

Round 7 已证明：短 ID、引用原文存在和数字匹配仍可能放过“标题是 Sable，解释和引用都是 Quill”，或者用告警卡支持配置值。本轮增加逐行的有限对象/字面配置检查，复核前提示缺口、复核后重算；未通过时保留原解释与判定，不伪装成资料本身不足。检查不理解通用谓词、别名、历史生效或来源权限。[完整适用边界](binding-development.md)。

同一轮还出现“对象不同，所以不能比较”的错误拒答。新复核上下文引用最近的原始用户问题与当前资料 ID，让模型重新查证两个讨论范围；不将旧助手答案提升为事实。用户明确要最小证据时，要求说明决定性观测及关联条件。仍用同一次 review、固定八行和原调用预算。[设计与开销](review-development.md)。

## 冻结前真实遇到的问题

1. 单侧提到另一个对象会误拦合法的代词对照，收窄为解释和引文同时仅提另一对象；未覆盖的语义明确记未验证。
2. 配置词法先漏掉句末 `2.`，又在复审中把 `2+1`、`2,000` 等截成 `2`。保留双向正反例，最终拒绝表达式前缀匹配，不执行模型表达式。
3. 旧上下文测试固定 18,000 单位，新增提示后提前在首次调用前超限。测试改为先测量首请求，再设置只够首次请求的隔离窗口，验证工具结果后停止；生产窗口和预算未提高。
4. 新 Agent 受控测试缺模型名，导致 review 前停止；补齐 fixture 后三条通过，无外部模型请求。
5. 评测器曾允许未列入 raw seal 的执行汇总参与评分。新增必须封存 `run-summary.json` 的检查，旧 raw/gold 不改。[工具记录](harness-development.md)。

最终 Python 1,423、Java 69（34 项真实 MySQL/Redis 集成）、UI 58 项通过；跨服务成功/超时最终 64/64。受控模型只在 loopback，6 秒实验预算不同于真实 75 秒，不能当作模型质量或商业流量。[工程验收与日志哈希](implementation-validation.md)。开发说明中“未冻结/未运行”属于当时的准备状态，实际执行状态以本页、候选清单和结果报告为准。

## 一次真实采集与异常处理

输入 46 文件与候选 68 源码/配置文件固定后，在隔离的 JVM 8083 / Python 8767、独立 MySQL 库与 Redis namespace 上运行。原 10 轮、16 份合成资料、两套 gold 不变；DeepInfra Qwen3-235B、BM25 top5、75 秒、6 decision + 1 review、输出 1800/2600。没有补采、换标签重跑或调高预算。

8 次提交、22 次尝试，Harbor 首轮失败后两轮依赖阻断；583 个原始文件封存，源码与输入前后身份一致。逐题阅读确认 6 份报告、1 次必要澄清。`kl-t2` 虽标为 `refused`，实际给出了有界证据不足结论，交付类型按正文记报告；不会因此算作正确回答。

Harbor 的第二次 decision 用时 39.189 秒，review 在第 44.248 秒开始，约余 30.752 秒；客户端等待后超时，worker 终态耗时 75.579 秒。没有返回 review 内容，provider 接受状态与用量未知。请求时限不是精确到毫秒的整体硬截止；调度/传输终止仍有少量超出。不能据此确认供应商故障、服务端继续生成，或把请求变大认定为超时原因。[逐请求时序](assessment/timeout-diagnosis.json)。

已知 token 下限 100,686，另有一次未知 review；调用次数为 15 decision + 7 review。未知不是零，也不能把下限换算成完整费用。[调用审计](assessment/call-audit.json)与[独立重算](assessment/independent-call-audit.json)。

## 封存后确认了什么

- ar-t2 三项比较已明确给出总尝试 2→3、重试 1→2、4xx 保持不重试，原“不同对象不能比较”拒答未出现；这是单次已暴露回归中的局部改善，不是因果消融或通用正确率。
- Cedar 原覆盖槽溢出不再发生，但两个整体结论仍被旧数量/因果规则降为不足。模型在原稿已将验收判定标成 `causal_claim`，不能仅凭提示变化推断为何误标。当前绑定检查 findings 为空，不意味着整体语义通过。
- KiteLoad 的错误配置引用不再作为 supported 发布，但多余配置行仍以历史缺证解释当前设置。最小证据说明比上一轮具体，报告范围与失败前提仍有缺口。
- Harbor 没有最终报告，不能用草稿宣称真实对象错配已修好。失败、依赖阻断和未知用量保留。

详见[原始失败排查](assessment/failure-review.md)、[内部独立阅读](assessment/independent-review.md)和[最终评分](REPORT.md)。原 gold 部分要求细于用户子问，评分者对是否必须显式重复背景项有分歧；保留原严格口径及分歧，不删除要求来制造通过。
