# 实际系统测试的解释

本次使用真实本机 JVM 服务、MySQL、Redis 和 Python HTTP worker。控制文档均明确标为 synthetic，任务均为 BM25 + extractive，不请求生成模型或 embedding 服务。运行 ID、精确依赖版本、源码及 JAR 哈希见 `summary.json` 与 `jar-runtime-manifest.json`。

## 已观察到的行为

13 项系统检查通过。16 个同时提交的相同幂等键得到 1 个新任务和 15 个复用响应，MySQL 中该测试工作区当时只有 1 个任务。相同键不同请求返回 409；从另一工作区访问该任务或文档返回 404。这验证数据范围约束，不是用户身份鉴权。

更新主文档并删除辅助文档后，已完成任务保留原有两份文档的结果和原快照版本，结果哈希不变；同一旧键仍返回旧任务。新键的新任务使用更新后的版本，结果包含新标记、排除旧标记及已删除文档。随后以另一新键提交相同请求，Redis 命中，当前执行的模型与嵌入调用数为零。该缓存控制使用 BM25，不能单凭本例验证非零历史模型账单；接口把历史来源用量和当前用量分开保留。

这份 HTTP 测试核对的是**已完成任务**在文档变化后的持久一致性。排队或执行中的任务在进程重启后的恢复需要单独故障实验，不在这里借用结论。测试保留全部任务、文档状态和 `restart-fixture.json`，没有清理数据库。

## 并发负载

32 个不同请求，由 8 个客户端闭环提交：每个客户端观察前一任务完成后才开始下一任务。问题和幂等键均不同，32 个结果全部为缓存未命中。32/32 成功，观察窗口 4.171 秒，含轮询开销的成功吞吐为 7.672 任务/秒。

| 指标 | p50 | p95 |
| --- | ---: | ---: |
| HTTP 提交耗时 | 6.075 ms | 14.667 ms |
| 客户端端到端（包括 100 ms 轮询） | 990.630 ms | 1097.673 ms |
| MySQL 时间戳计算的排队时长 | 958.017 ms | 1015.820 ms |
| Worker 执行记录 | 2 ms | 3 ms |

运行前进程最大活跃 worker 为 1，运行后为 2，配置上限为 2。原始轮询样本与服务的进程最大值均保留；单靠轮询可能遗漏短时峰值，因此报告使用进程计数器核对上限。

**当前主要等待发生在队列。** 排队时长接近端到端时间，而 worker 只有数毫秒；源码中的调度周期为 250 ms、worker 槽位为 2，与此小负载下观察到的约 8 个任务/秒相符。这提示后续可研究任务完成后及时补位的调度方式，但本轮没有对调度机制做对照修改，不能把全部等待因果归于单一因素。

这不是最大吞吐测试：只有一个本机 JVM、小型人工文档、回环网络、32 个短任务，没有持续压力或复杂生成任务。不能据此声称支持高并发生产流量或 LLM 推理吞吐。p95 来自 32 个样本的线性插值，只描述本次运行。

## 复现和证据

```bash
python scripts/evaluate_workspace_system.py --self-test
python scripts/evaluate_workspace_system.py \
  --endpoint http://127.0.0.1:8081 \
  --environment-json .local/environment.json \
  --output docs/evaluations/v0.12/system-new-run
```

版本与硬件 JSON 仅含经过整理的运行环境信息，不应填入凭据。每次使用新目录和新 UUID 工作区；旧输出拒绝覆盖。`observations.jsonl` 保留 426 条实际 HTTP 观察，包含提交、状态轮询、最终任务和指标。源码与同一个 JAR 在本轮前后哈希相同；JAR 内 72 个依赖及 classpath 一并记录。没有重试、替换失败、模拟数据库或隐含模型调用。
