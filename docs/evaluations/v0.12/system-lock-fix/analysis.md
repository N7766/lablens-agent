# 调度与锁竞争修复后的三轮复测

**三轮各 13/13 系统检查通过，三批负载合计 96/96 成功。** 每轮沿用同一个未修改的 HTTP 评测器、32 个不同 BM25/extractive 请求、8 个闭环客户端、100 ms 轮询和相同人工文档模板；只替换 UUID 工作区和幂等键。没有重试外部调用、删除失败历史或挑选最好一次。模型和 embedding 调用均为零，96 个负载任务全部缓存未命中，进程最大活跃 worker 保持 2。

首次事件唤醒确实缩短等待，但暴露一个 `CannotAcquireLockException`，原 31/32 结果仍保留。修复版本调整过期任务处理的索引和按主键写入、任务领取事务隔离、周期与事件调度的串行合并，并对有限 SQL 完成操作设置有限重试；不会为修复数据库写入而重发外部模型请求。这一轮没有重新出现任务失败。死锁机制的定位由数据库故障记录和实现检查支持；这里的三次 HTTP 复测负责核对修复后实际行为，不单独证明每项改动的因果贡献。

排队耗时持续落在数毫秒，符合及时补位的设计目的。客户端 p50 与吞吐仍明显波动，尤其第一轮有较多请求跨过 100 ms 轮询间隔；数据库、JIT 和连接预热也没有做随机化隔离。因此保留所有三轮值，不能只引用最高 172.184 作为系统稳定容量。原基线只有一次，修复版本三次，并非均衡的大规模性能实验。

工作负载是单机回环、小文档、短任务。结果能够支持“发现真实并发失败、定位锁竞争、修复并重复验收”的工程证据，不能推出生产 SLA、真实用户并发、生成模型吞吐或一般性的加速倍数。

## 完整性与复现

三轮使用同一 JAR、同一源码字节，运行前后哈希均不变；Python RAG 与评测脚本也和原基线一致。不同版本 JAR 同时含前端资源更新，但该 HTTP 评测没有访问前端，不把它称为只改一个变量的严格因果实验。原始 HTTP 观察分别为 140、114、119 条，各目录 `observations.jsonl` 全部保留。

当前目录的 `frozen-source-manifest.json` 关联三个运行 ID、16 个相关实现/迁移/评测源文件和 JAR 哈希；`jar-runtime-manifest.json` 记录 72 个运行依赖与 classpath。每轮另有完整 `summary.json`、`report.md`、`restart-fixture.json`。

```bash
python scripts/evaluate_workspace_system.py \
  --environment-json .local/environment.json \
  --output docs/evaluations/v0.12/system-new-run
```

每次复现使用新目录，脚本拒绝覆盖已有结果。数据库中的已完成任务与文档保留，可继续用各轮 restart fixture 做只读持久化核对。
