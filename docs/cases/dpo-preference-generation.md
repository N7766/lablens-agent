# 真实排查案例：偏好指标改善，为什么自由生成没有跟着变好？

本案例复核已有 DPO 研究记录，未重新训练、调用模型或修改源实验。结论是：**偏好目标优化与最终生成任务表现确实分离，但现有材料不足以确定唯一根因。** Stage 4 的训练偏好指标从早期到后期改善，最终偏好验证准确率为 1.0；自由生成却只有 153/462，而另一路线 Stage 3 SFT 是 439/462。这里的“下降”是跨路线对比，不是同一 SFT 权重继续 DPO 的前后因果对照。

证据包：[`evaluation/cases/dpo`](../../evaluation/cases/dpo/README.md)。原仓库为
[`N7766/dpo-cot-compression`](https://github.com/N7766/dpo-cot-compression)，
当前代码/配置/公开报告快照对应提交 `0821ef3bca3eb117cab778a26416c820ebe73f26`。
历史日志和生成结果原先由源仓库忽略，本次仅收录已检查、不含个人资料的研究档案。
当前源码与历史日志分别标记，不能用此提交号证明历史 GPU 运行使用了同一版本。

## 1. 先把三种指标分开

| 观察 | 档案值 | 能说明什么 |
| --- | --- | --- |
| Stage 4 训练日志，第10步 → 第180步 | preference accuracy 0.55625 → 1.0；margin 0.09156 → 21.31781 | 首尾训练批次日志聚合改善；中间并非严格单调 |
| Stage 4 偏好验证，第100步 → 第181步 | accuracy 1.0 → 1.0；margin 21.52156 → 21.66945 | 验证 accuracy 已经饱和，并未继续增加 |
| Stage 3 SFT 自由生成 | 439/462 = 95.0216% | 存档回答按现有答案提取与判分规则的正确率 |
| Stage 4 full DPO 自由生成 | 153/462 = 33.1169% | 同462个ID及gold下低于SFT路线61.9048个百分点 |

来源片段：`e_first_train`、`e_last_train`、`e_eval_100`、`e_eval_181`、
`e_sft_summary`、`e_dpo_summary`，逐条文本/原路径/行号见
[`excerpts.json`](../../evaluation/cases/dpo/excerpts.json)。

严格偏好验证有 **320 对**，自由生成比较有 **462 题**。偏好分数针对已有
chosen/rejected 候选的相对关系，自由生成分数针对模型实际生成的答案，既非同一任务，
也非同一分母。日志的 1.0 不代表462题全部回答正确。没有保存的逐对预测时，也不把
日志聚合值倒推出一份不存在的320条逐对结果。

最终验证 chosen reward 为 **−1.52227**、rejected reward 为 **−23.19172**，
相差 **21.66945**。较大的 margin 与两侧 reward 同时为负并不矛盾；它不要求
chosen 的 reward 为正，更不证明自由生成能力提高。本案例不重新执行历史 TRL，
也不据此宣称已经确定“压低 rejected”是生成低分的唯一机制。

## 2. 核对比较对象：SFT 基线确实存在，但 Stage 4 不是它的续训

SFT 基线并非缺失。当前配置、正式 Stage 3 报告、checkpoint-253 的训练状态，
以及完整462条自由生成输出都在证据包中。训练状态最终 eval loss 为0.2007074；
这与自由生成439/462是不同评估指标。

| 条件 | Stage 3 SFT | Stage 4 full DPO |
| --- | --- | --- |
| 记录的路线 | 基座 + LoRA SFT | 基座直接 full DPO |
| 训练资料数量 | 4048条SFT响应 | 2894对严格偏好 |
| 对应训练验证资料 | 451条 | 320对 |
| 自由生成文件 | 同一 Stage 1 preference validation 文件标签 | 同左 |
| 自由生成样本 | 462 | 462 |
| `max_new_tokens` | 128 | 128 |
| 生成 batch size | 32 | 16 |
| 已保存的优化步数 | 253 | 181 |

Stage 4 历史启动日志记录 `Base model: Qwen/Qwen3-8B`；正式报告也写明
base → full DPO。当前配置与训练入口直接加载该基座，未见 SFT adapter 加载/合并。
多类证据相互一致，因此不能把两条路线包装成“同一个95%准确率的SFT模型被DPO训坏”。
同时，档案没有历史权重内容指纹和完整运行环境锁；当前配置/源码仍不是历史执行的
逐步证明。参见 `e_training_header`、`e_training_loader`、`e_stage4_route`。

**更重要的反证：基座40题本来就只有13/40。** 其记录同样指定128预算，使用同一
验证文件标签，batch为4。按ID和gold对齐，Stage 4在这些40题上为12/40。
这不是严密控制实验，也不能证明DPO完全无害；但它使“低分只由DPO破坏一个原本95%的
模型导致”的解释缺少依据。不能把早期 API 的其他提示/子集成绩作为此处基座对照。
源README已明确指出这些早期实验口径不同，并要求另做受控评测（`e_controlled_plan`）。

## 3. 检查汇总、评分器与原始回答

对SFT462条、Stage4的462条和基座40条，共 **964条**保存输出逐一复算：

- 提取答案、正确标记和空白词数，三组均为 **0 个字段不一致**。
- SFT与Stage4的ID和gold逐项同序；配对为两者都对150、仅SFT对289、仅DPO对3、两者都错20。
- 439/462、153/462及13/40与各自原始汇总一致。
- 原字段 `output_tokens` 实际与 `len(prediction.split())` 一致。均值32.4221和79.6775应写作**空白分隔词数**，不是 tokenizer token，也不是时延。

复算能排除“本案存档汇总加错”或“保存字段与当前评分规则不一致”。它不能证明答案
提取协议最佳、gold无误、全部自然语言推理正确，也不能证明历史运行代码与当前快照相同。

三个可定位的描述性例子：

| 样本 | 保存的行为 | 可得结论 / 不能得的结论 |
| --- | --- | --- |
| `train_36` | 先写 `Answer: A`，后继续推演；解析器取随后数字60，gold为15 | 可定位格式/提取交互；不能直接当作模型最终认为答案60 |
| `train_64` | 写 `Answer: 800` 后重新计算，保存文本未完整结束；gold840 | 确有错误早期答案与续写；未记录停止原因，不能断言必然128-token截断 |
| `train_79` | 已写正确70后又续写，保存尾部未完成，但最终判分仍正确 | 续写或不完整尾部不必然导致错误，不能仅按外观归因 |

这些样本是排查例子，不是随机抽样，不用于估计某类失败占比。
对应 `e_bad_option`、`e_early_wrong_answer`、`e_continuation_but_correct`；
完整输出仍保留，未删除反例。

## 4. 配置不等于生效参数：本案有实际反例

当前 Stage 4 YAML 写 `max_prompt_length: 512`，但历史训练日志明确记录：

> Warning: installed TRL DPOConfig does not accept these config keys; ignoring them: max_prompt_length

这是源项目自己的日志片段（`e_ignored_prompt_setting`）。因此不能写“已经核验训练
prompt被限制到512”。警告也不告诉我们实际替代默认值，不能进一步把生成低分归因于它。
这个冲突说明参数表、代码路径和实际运行记录需要分别检查。

## 5. 逐结论判定

完整机器映射位于 [`claims.json`](../../evaluation/cases/dpo/claims.json)，每条都有
`evidence_ids`、理由和范围。以下“矛盾”针对具体表述，不把所有原因都排除：

| ID | 待判表述 | 判定 |
| --- | --- | --- |
| C01 | 首尾训练偏好日志改善 | 支持 |
| C02 | 偏好验证1.0等于自由生成全对 | 矛盾 |
| C03 | 对齐462题上Stage4比SFT路线低分 | 支持，但仅跨路线 |
| C04 | SFT基线资料不存在 | 矛盾 |
| C05 | 已证明同一SFT权重继续DPO导致下降 | 与现有路线记录矛盾；历史权重身份仍有限 |
| C06 | 最终margin为正，所以chosen reward也为正 | 矛盾；两侧reward均为负 |
| C07 | 过优化/灾难性遗忘是已确定的唯一根因 | 证据不足 |
| C08 | 保存汇总或当前评分复算不一致造成分差 | 与964条复算矛盾；协议偏差未排除 |
| C09 | 单独由128-token预算截断导致 | 证据不足 |
| C10 | 输出长度记录是token或时延 | 矛盾 |
| C11 | 配置的512 prompt限制历史生效 | 与历史忽略警告矛盾 |
| C12 | 已排除提示协议或评分规则影响 | 证据不足 |
| C13 | 462题是官方独立test | 与数据来源/内部划分记录矛盾 |
| C14 | 已排除泄漏、错权重或FSDP数值问题 | 证据不足；本案也没证明存在这些故障 |
| C15 | 验证accuracy继续上升且生成逐检查点下降 | 矛盾；验证accuracy两点均1.0，生成无同步曲线 |

记录来自 GSM8K train 内构造并筛选后划分的偏好验证资料，不能当独立官方test。
本包不包含原始训练集，也不伪称已做完数据泄漏审计。

## 6. 下一项能区分解释的实验（未执行）

1. 冻结实际模型/adapter内容指纹、tokenizer、运行依赖、提示、ID、评分脚本和参数；
   同一运行条件评基座、SFT与各DPO检查点，先消除跨路线和batch混淆。
2. 同时保存实际生成token数、停止原因及完整输出；在开发题上比较固定预算和提示协议，
   将格式失败、未完成生成和完整错误答案分开标注，而不是仅凭末尾文本猜截断。
3. 若要测试“DPO从SFT继续后退化”，必须新增真正SFT初始化的对照并控制其余条件；
   若比较学习率、beta或训练步数，则预声明变量与选择规则，最后在未参与选择的新题上验证。

这些是排查计划，不是本轮已获得的提升。本轮实际完成的是**来源追踪、指标分离、
基线补查、原始结果复算、反证保留和可重复的离线证据包**，不能据此宣称已经修复训练模型。

## 7. 复核与使用

```sh
# 不需要DPO源仓库、GPU、API密钥或第三方依赖
python scripts/verify_dpo_case.py --self-test

# 若本机保留源档案，可额外只读核对原文件SHA与片段
python scripts/verify_dpo_case.py --source-root /path/to/dpo-cot-compression
```

脚本检查文件哈希、原行片段、引用映射与数值，**不自动判定自然语言结论或根因**。
15条结论由参与工作的助手整理，并由另一个助手只读交叉检查关键档案；这不构成
独立人工盲评。哈希不是签名，也不认证来源。源DPO的未提交论文/PPT、个人学历资料、
权重及密钥均未纳入，源仓库未修改。

适合面试的窄表述：

> 我用LabLens整理了一次真实DPO负结果的排查证据：分开偏好排序与自由生成指标，
> 找到了已有SFT和基座对照，复算964条保存输出，并定位到“配置512但运行忽略”与
> “不同训练路线被误当成同一模型前后变化”两类证据问题。当前证据支持继续做受控
> 实验，不支持把过优化认定为唯一原因。

其中训练与原始实验成果属于DPO源项目；本次证据整理与离线核验属于LabLens案例。
个人表述仍应以能够自行解释、复现和修改的实际参与为准。
