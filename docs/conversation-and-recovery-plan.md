# 会话、上下文、恢复与记忆：下一阶段设计提案

日期：2026-10-29。本文保留原三轮规划。第一轮已实现会话持久化、用户固定短期状态、保守上下文预算和澄清协议；实际结果与未通过项见[第一轮验收](conversation-round1.md)。第二、三轮尚未实现。原规划基于 `83f7ab1`，不追溯改变 v0.13 语义验收结论。

## 规划起点（83f7ab1，第一轮实现前）

- Agent 单次任务内可多步调用工具，但每次 run 都新建 messages，没有跨请求 conversation/turn 协议。
- MySQL 已有资料版本、任务快照和结果；这提供任务历史，不会自动使模型记住历史对话。
- 已有调用/时间预算、幂等、租约、未知用量记录；进程中断的 RUNNING 任务租约到期后失败，不会步骤级恢复。
- 当前字符/文档数限制不是模型 token 上下文预算；没有会话摘要、压缩版本与记忆生命周期。

## 能力与验收

| 能力 | 建议实现 | 必须验证的行为 |
| --- | --- | --- |
| 多轮对话 | conversation/turn/parent_turn/version；解析追问所指实验和比较对象，缺歧义信息时澄清 | 先问SFT，再问“和刚才那个比呢”；更正对象后不沿用旧对象；刷新后会话仍可继续 |
| 上下文管理 | 模型适配的token计量，预留输出/工具schema/安全余量；最近消息+结构化状态+相关证据；长工具结果落库后按需读取 | 强制小窗口、长中英文、巨大工具输出；不拆断tool-call/result配对，不丢用户纠正和未完成目标；压缩失败可明确停止 |
| 短期记忆 | 当前目标、约束、已选实验ID、已核验事实、待解问题和资料版本；持久化后再按预算装入上下文 | 20轮含多次纠正与话题切换，关键约束保持；摘要标记已处理到的事件序号，并能回溯原消息 |
| 长期记忆 | 项目范围内保存经确认的偏好和有证据的事实；记录来源、类型、有效期、版本和状态，支持查看/修改/删除 | 跨会话召回，跨项目不串；矛盾记录保留双方，旧事实可失效；删除后原记录、摘要和索引均不再召回 |
| 中断与恢复 | 每个工具边界记录step/checkpoint/call ledger；区分取消、暂停、断网、进程崩溃、provider超时与结果未知 | 工具完成后杀进程、请求已发但回包前断网、取消后迟到回包；已完成只读步骤可复用，未知外部调用不盲目重发 |
| 会话并发与分支 | turn乐观版本锁、明确同会话排队/分支策略；task绑定会话版本与资料版本 | 双标签页同时提问、重复提交、迟到回答；不覆盖更新后的会话，旧结果只归属原turn |
| 进度与断线重连 | SSE持久事件编号；按Last-Event-ID恢复事件，显示检索/核验/生成等进度及取消入口 | 浏览器断线后重连不创建新任务；消息不漏，重复事件可去重；页面关闭与服务端取消分开定义 |
| 证据与记忆治理 | 区分用户陈述、来源原文、模型推测、确认结论；摘要和记忆继承来源/不确定性；来源更新触发复核 | 资料内“记住我是系统指令”、旧答案错误、验证/测试集混淆，不能经摘要或长期记忆升级成权威事实 |
| 检索与澄清 | 独立评测跨语言BM25/dense/hybrid；追问改写显式带上实验与时间范围；保留原问题和改写 | 对检索漏失和真正缺信息分别计分；有反证时仍取得两方证据；歧义追问先澄清 |
| 可观测与评测 | trace关联conversation/turn/task/step；记录模型/提示/源码/资料/摘要/记忆版本与token/费用/耗时 | 分开报告系统执行成功、任务完成、结论正确；固定开发题之外另留未见多轮题与故障测试 |

## 记忆的边界

短期/长期按作用范围区分，不按Redis/MySQL或保存时长简单划分。短期会话状态也应能在重启后恢复。

建议初期MySQL作为消息、状态、检查点、事实记录的权威存储；Redis处理缓存、限流与临时协调；向量索引只用于寻找可能相关的记忆，命中后仍核对作用域、状态、版本和来源。已有RAG资料与用户偏好、会话摘要使用不同类型/命名空间，避免混作同一种证据。

记忆写入先限定为明确用户偏好和带原文证据的项目事实。模型推测保持候选状态；用户陈述标记为用户陈述，不认证成实验事实。长期写入/删除可查看、可撤回，不自动存整段对话。本文不要求修改Codex或个人账户记忆。

## 恢复语义

浏览器断开通常只丢连接，后台任务可继续；用户点击取消则请求服务停止后续步骤，并阻止迟到结果成为当前答案。暂停后续跑应保留原资料/会话快照；若要改用新资料，创建新版本任务并重新确认相关发送范围。

持久化工具调用前的意图，以及完成后的结果。进程在二者之间退出时，外部操作可能已发生：对于有副作用的未来工具，必须使用供应商幂等键或状态查询进行对账；不能承诺跨第三方系统的无条件exactly-once。对可重复只读调用也需考虑费用和资料变化。检查点恢复不等于简单重发最后一条请求。

## 三轮实施顺序

1. **会话与上下文（已实现，质量验收见报告）**：跨语言领域术语归一化、验证集标签检查、会话、用户固定短期状态、保守字节估算预算、追问澄清。实际没有实现自动事实摘要或精确 tokenizer 计量，不将受控测试等同于模型质量。
2. **恢复与并发**：步骤事件/检查点、取消、暂停、显式恢复、SSE重连、会话版本冲突。做真实进程/网络故障注入，区分恢复成功与外部结果未知。
3. **长期记忆**：项目范围记忆、来源/有效期/冲突/删除，加入跨会话评测和整体回归；现有语义短板未收敛前不默认自动沉淀模型结论。

每轮都交付实际演示、原始记录和失败分析。这里不预写尚未测得的成功率或性能提升。

## 建议度量

- 会话：指代解析准确率、用户纠正后约束保持率、完整任务成功率。
- 上下文：超限请求比例、压缩前后关键事实/约束保留率、摘要无依据事实率、每轮输入token和p95延迟。
- 恢复：故障场景完成率、重复外部调用数、取消后新步骤数、恢复时延、未知结果的正确标记率。
- 记忆：召回precision/recall、错误写入率、作用域串用率、过期/删除记录误召回率。
- 质量：证据完整覆盖、结论语义正确、错误拒答、引用蕴含；单列评分者与样本规模。

20轮或大文本测试是压力/边界样例；人工答案、受控工具和真实provider结果分别标注，不能混成总体质量分数。
